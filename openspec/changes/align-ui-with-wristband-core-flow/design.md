## Context

两个前端目前都是独立的 Vue/Vite 演示应用。会员管理端已有会员 CRUD、金额充值和全局时长设置，但缺少实体手环办理流程；自助端已有手机号、资料、刷环和成功页面，但没有会员查询分支或手环状态校验。两个应用运行在不同开发端口，本 change 不引入后端，因此跨应用实时共享数据不在本轮实现范围内。

## Goals / Non-Goals

**Goals:**

- 用一致的业务词汇展示 `EMPTY → CHARGED → READY → ACTIVE → EXPIRED` 手环状态。
- 让会员管理端可完整演示充时、柜台识别/注册会员、激活、查询和归还。
- 让自助端可演示已有会员直达激活、新会员登记后激活，以及非 CHARGED 手环被拒绝。
- 将本次购买时长归属到手环，而不是会员。
- 最大限度复用现有页面、组件和视觉样式。

**Non-Goals:**

- 不接入 Spring Boot、SQLite、真实 API 或跨应用同步。
- 不接入真实读卡器、支付渠道、打印机或 Electron。
- 不实现游戏端首次刷卡、真实倒计时持久化、审计或历史流水。
- 不重构与核心闭环无关的房间、排行和游戏配置演示页。

## Decisions

### 1. 管理端增加独立的“手环办理”工作台

手环充时发生在会员识别之前，因此不能继续藏在会员详情的“充值”按钮中。新增一级入口承载三块内容：充时表单、柜台激活表单、当前手环状态表。工作台默认作为管理端首屏，突出门店最高频操作。

### 2. 会员模型不保存金额和手环时长

`Member.rechargeAmount` 与 `Member.braceletMinutes` 从类型和会员 UI 中移除。付款发生在系统外；购买分钟数记录在当前手环上。系统设置中的时长选项仅作为充时表单的快捷值，不再表达全店统一规则。

### 3. 单一手环状态机

演示数据只维护一个 `Wristband.state`：

- `empty`：待充时
- `charged`：已充时待激活
- `ready`：已绑定会员，待首次游戏刷卡
- `active`：计时中
- `expired`：已到期，待归还

归还会清空本轮会员、时长和时间字段并回到 `empty`。本 change 不维护另一套绑定状态，避免 UI 内部双状态同步。

### 4. 管理端与自助端各自维护可预测的模拟状态

两个 Vite 应用在开发态属于不同 origin，浏览器存储无法可靠共享。本轮各自使用相同格式的本地种子数据和明确的演示 UID，分别验证页面分支。未来接入 API 时由后端 SQLite 成为唯一数据源，替换模拟存储而不改变页面流程。

### 5. 自助端把会员查询并入主激活路径

手机号确认后先查模拟会员：存在则显示简洁的身份确认页，不存在才显示完整注册页。两条路径最终汇合到刷环页。原首页“Player Info Query”不作为 MVP 独立流程。

### 6. 自助刷环显式输入模拟 UID

保留读卡动画，同时增加演示 UID 输入和快捷样例，使测试者能够验证成功、未充时和已激活等分支。只有 `charged` 手环会进入成功页，成功时显示该手环实际分钟数。

## Risks / Trade-offs

- [两个应用的模拟数据不会实时同步] → 页面明确标注独立 UI 演示；后续接入 SQLite API 时再实现真实共享。
- [管理端增加新页面使现有导航更拥挤] → 将其设为默认入口，并保持其他演示页面不变。
- [移除会员金额和时长会影响记录页字段] → 会员列表和详情只展示身份资料；交易演示记录保持独立，不再暗示会员余额。
- [状态 `active` 无真实计时来源] → 仅使用种子数据展示；本轮不模拟游戏端状态转换。
