## Why

一台会员管理端最终要同时接收多个自助注册端和游戏端的数据，但现有验收不能证明多台机器并发注册、绑环、开局和结算时 SQLite 不会丢记录、重复记录、绑错会员或算错积分。需要一套能够在三台 Windows 机器上直接运行、结果可以精确核对的打包版并发验收脚本。

## What Changes

- 提供 A 机启动脚本，用现有运行参数启动同一份会员管理端打包程序，但为每次运行分配独立 userData、SQLite、日志、测试端口和 `TEST` 备份目录。
- 提供一份 B/C 通用便携脚本，由两台机器使用相同 runId、不同 agentId，持续模拟可配置数量的自助注册端和游戏端调用现有生产 HTTP 接口。
- 每台代理在运行前生成完整确定性计划，运行后输出请求结果；核心正确性测试不自动重试写请求，避免重试掩盖丢失或制造重复。
- 提供 A 机核账脚本，读取两台代理复制回来的结果，通过公开查询接口逐项核对会员、手环绑定、游戏记录、结束状态和积分，并生成中文报告。
- 会员管理端在测试启动参数存在时明显显示测试模式和 runId；正常启动使用的数据库及正式备份不参与测试。
- 测试数据默认保留在本次运行目录中。恢复正常使用只需关闭测试实例并正常启动会员管理端，不提供逐条清理或自动删除数据库功能。

## Capabilities

### New Capabilities

- `multipoint-concurrency-acceptance`: 定义隔离启动打包版中心应用、两机并发业务脚本、确定性计划、精确核账、中文报告和覆盖边界。

### Modified Capabilities

无。

## Impact

- `F:/project/ledGame-platform`: 增加中心启动器、并发代理、核账器、便携构建、测试模式标识、自动化测试和中文说明。
- 复用现有 `LEDGAME_USER_DATA`、平台端口、备份环境与 root override，以及 `/api/members`、`/api/wristbands/**`、`/api/game-access/activate` 和 `/api/game-plays/**` 等公开接口。
- 不新增协调服务、代理注册协议、数据库表、生产业务接口或自动数据清理能力。
- `F:/project/ledGame` 与 `F:/project/ledGame-backend` 默认不修改；直接平台调用验证中心数据库并发，不代表已经覆盖真实客户端 UI、本地游戏后端、房间连接或硬件。
