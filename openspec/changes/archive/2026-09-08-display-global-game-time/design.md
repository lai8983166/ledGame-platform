## Context

游戏实体已经保存 `globalTimeLimit` 和 `globalTimeLimitValue`，运行时也能从排除暂停时段后的总运行时长计算全局剩余时间。不过当前通用运行时快照没有计时投影：副屏仅直接读取 Rank 玩法的 `gameplay.remainingMillis`，会员管理端又把房间 `remainingSeconds` 固定映射为 `0`。

副屏通过游戏 backend 的运行时 WebSocket 接收高频状态；会员管理端则通过另一条以来源 IP 识别房间的 WebSocket，只在快照和关键业务事件上保存最后状态。房间连接必须继续承担在线判断和关键状态同步，不能为显示倒计时增加每秒跨机器上报。

## Goals / Non-Goals

**Goals:**

- 用一个独立于 `simple`、`normal`、`diffcult`、`rank` 的通用计时投影表达有限、无限、运行和暂停。
- 让副屏直接消费权威运行时快照，让会员管理端从关键节点锚点本地推导秒级显示。
- 复用游戏引擎现有的暂停时间扣除语义，确保关卡结算等暂停阶段不会消耗全局时间。
- 对旧游戏端或旧房间快照保持向后兼容。

**Non-Goals:**

- 不改变玩法是否必须配置全局时间，也不为未配置的玩法强行添加默认时限。
- 不展示或修改手环余额、会员可用时长及其扣减规则。
- 不改变玩法自己的关卡计时、Rank 回合计时或游戏结束判定。
- 不增加计时数据库表，不持久化逐秒倒计时，也不要求断电后恢复未完成游戏。

## Decisions

### 1. 在通用运行时快照增加 `gameTime` 投影

`GameRuntimeStateService` 输出可选对象：

```json
{
  "gameTime": {
    "mode": "LIMITED",
    "remainingMillis": 598000,
    "running": true
  }
}
```

无限模式使用 `mode: "UNLIMITED"`、`remainingMillis: null`，而不是以 `-1`、极大数或字段缺失表示无限。有限剩余时间由配置秒数减去 `GameContext.getTotalRunTime()` 得到并钳制到零；`running` 只有在全局计时实际推进时为真。没有活动或可展示游戏时 `gameTime` 可以为 `null`。

选择通用顶层投影而不是把字段继续放进 `gameplay`，因为后者由各玩法自行定义，已经存在 Rank 局部倒计时等不同语义。顶层投影能防止新增玩法遗漏计时展示。

### 2. 副屏消费权威快照，不建立第二套游戏时钟

游戏 backend 已随运行帧广播 action `12` 状态，副屏在展示有限时间时读取最新 `gameTime.remainingMillis`，暂停后则使用生命周期快照中的冻结值。副屏可以仅用本地小间隔刷新格式化结果以平滑跨秒显示，但不得自行决定游戏是否超时；真正的结束判定仍归游戏引擎。

Rank 原有 `gameplay.remainingMillis` 保留为玩法内部的回合/阶段数据，但从通用“游戏剩余”位置移除，避免与全局时间混淆。

### 3. 房间连接同步计时锚点而不是逐秒值

房间事件中的通用 runtime state 自动携带 `gameTime`。除现有 `GAME_STARTED`、`GAME_ENDED` 和重连 `ROOM_SNAPSHOT` 外，在全局计时从运行变为暂停、从暂停恢复运行时增加房间状态事件。它们属于影响房间可见状态的关键节点，而不是心跳或逐秒遥测。

会员平台在接受事件时继续使用平台服务端生成的 `lastEventAt` 作为锚点接收时间。这样管理端无需比较游戏桌面端和会员管理端两台机器的系统时钟，避免局域网设备时钟不一致造成倒计时跳变。

### 4. 会员管理端以锚点和本地时钟派生显示值

房间状态映射保留以下展示模型：计时模式、锚点剩余毫秒、是否运行以及平台接收锚点时间。界面使用一个本地一秒 tick 触发重算：

- `LIMITED + running`：`max(0, anchorRemaining - (now - lastEventAt))`
- `LIMITED + paused`：固定使用 `anchorRemaining`
- `UNLIMITED`：显示“无限”
- 缺少 `gameTime`：显示 `--`
- 空闲或结束：隐藏当前局时间

房间 API 的两秒刷新继续负责在线状态和新关键事件，不为了倒计时提高请求频率。详情抽屉不保存一份会过期的 Room 副本，而是按房间 ID 从最新 rooms 集合派生，保证打开期间也能收到暂停、恢复和结束状态。

### 5. 统一格式化和边界行为

两个前端各自在其仓库内提供经过同一契约测试覆盖的纯格式化函数。正的不足一秒剩余值向上取整为 `00:01`，零显示 `00:00`；不足一小时显示 `MM:SS`，达到一小时显示 `HH:MM:SS`。本次不引入新的跨仓库共享包，以免只为一个小型纯函数增加发布和版本协调成本。

## Risks / Trade-offs

- [关键暂停/恢复事件遗漏会导致管理端继续错误倒计时] → 将房间计时事件挂在统一生命周期/计时状态转换点，并用暂停、恢复和多关卡测试覆盖，而不是在各玩法中分别调用。
- [事件在网络中有少量延迟] → 平台以接收时间建立锚点；显示可能比游戏端慢一个网络延迟，但不会受设备时钟偏差影响，也不会持续累积误差，下一关键事件会重新校准。
- [会员管理端页面长时间不刷新导致事件状态过旧] → 房间 API 保持现有周期刷新，本地 tick 只负责显示；重连快照负责恢复运行中的权威锚点。
- [旧游戏端没有 `gameTime`] → API 字段保持可选，UI 显示 `--`，不把未知错误解释成零或无限。
- [副屏高频状态和本地 tick 重复刷新] → 展示层只在可见秒数变化时更新文本，权威状态仍来自 backend。

## Migration Plan

1. 先发布能够容忍 `gameTime` 缺失的平台 API 类型和会员管理端 UI。
2. 发布输出统一计时投影及关键节点事件的游戏 backend。
3. 发布消费统一投影的游戏端副屏。
4. 使用有限、无限、暂停/恢复和运行中重连场景进行三端验收；确认旧游戏端连接时只显示 `--` 而不报错。

回滚任一客户端时，新字段会被旧消费者忽略；回滚游戏 backend 后，新消费者退回兼容占位，不需要迁移数据库。
