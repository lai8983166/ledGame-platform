## Why

会员、手环余额、积分、账号和营业记录目前只保存在会员管理端的一份 SQLite 数据库中，数据库误损坏或所在物理硬盘故障会造成门店数据不可恢复。门店机器若具备第二块物理硬盘，系统应当在不增加管理员配置负担的前提下自动建立可验证、可恢复的异盘备份。

## What Changes

- 会员管理端根据 `platform.db` 的实际位置识别其所属 Windows 物理硬盘，而不是根据应用安装盘或盘符推断。
- 自动选择另一块符合条件且可写的本地固定物理硬盘，并在其根目录创建固定的会员管理端备份目录；不要求管理员选择或确认目录。
- 使用 SQLite 一致性备份能力，在关键业务写入后更新最新备份，并保留带时间戳的历史快照，避免简单复制正在写入的数据库文件。
- 在主数据库中维护随已提交业务变更单调递增的数据库版本，备份携带同一版本，以此判断主库与备份是否同步；文件哈希只用于验证既有备份文件是否被修改或损坏。
- 会员管理端启动时先显示独立的备份检查窗口，完成主库完整性、备份完整性、数据库身份和版本比对及必要的追赶备份后，才显示主界面；不可安全自动处理的冲突停留在检查窗口。
- 仅向已登录的出厂账号提供从自动发现的 latest/历史备份或本地选定备份文件导入并覆盖主数据库的维护功能；启动检查窗口只报告检查结果，不提供导入入口。系统先读取版本和最后业务修改时间并验证候选库，再弹窗确认“要将版本为 xx，最后修改时间为 xxx 的数据库导入吗？”。
- 导入时暂停三端写入、保留被覆盖主库的回滚副本、原子替换并重新启动检查；导入失败自动恢复原主库，成功后使用导入数据库的账号和业务数据重新进入系统。
- 正常关闭会员管理端时，如果仍有未备份变更，则在有界等待时间内执行收尾备份；强制终止后的未同步状态在下次启动检查时处理。
- 对备份执行完整性验证、保留期清理和恢复验证，确保备份不仅存在，而且能够实际打开并还原业务数据。
- 在会员管理端展示备份状态、目标磁盘、最后成功时间和可操作的失败原因；第二块硬盘缺失、不可写或空间不足时不阻断营业。
- 为物理磁盘识别、目标选择、备份一致性、故障恢复和保留策略增加自动化测试，并定义真实双物理硬盘 Windows 机器的验收步骤。
- 将生产备份与自动化/硬件验收测试备份按目录和元数据环境双重隔离，允许测试真实生成并保留备份，但生产程序不得将测试备份识别为冲突或导入候选。
- 为有效主库与异身份/更高版本备份冲突增加“保留当前主库并重新建立正式备份”的出厂维护动作，避免界面把导入表现为唯一处理方式。
- 导入前验证候选数据库具有唯一且启用的出厂账号，并展示出厂账号名和会员数量，避免导入后因未知账号而失去管理权限。
- 修复会员管理端隐藏启动窗口导致关闭后 Electron/Java 残留的问题，并增加单实例与端口释放验证。

## Capabilities

### New Capabilities

- `automatic-cross-disk-database-backup`: 覆盖 Windows 异物理硬盘识别、SQLite 自动备份、历史保留、运行状态、故障恢复和配套测试要求。

## Impact

- 会员管理端 Electron 主进程需要增加启动检查窗口、退出协调、备份状态转发和诊断接口。
- 平台后端需要增加数据库身份与单调版本、Windows 磁盘拓扑探测、备份调度、一致性备份及启动门禁。
- 会员管理端设置或运营界面需要增加备份状态与明确的异常提示。
- 测试范围涉及 Node/Electron 单元测试、真实 SQLite 集成测试以及双物理硬盘 Windows 人工验收。
- 不修改自助注册端、游戏端及其本地数据，也不引入云服务、网络存储或第三方备份平台。
