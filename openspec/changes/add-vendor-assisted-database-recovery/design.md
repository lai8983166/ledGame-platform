## Context

当前会员管理端使用随机门店数据密钥对敏感字段和头像进行 AES-GCM 加密，并用当前 Windows 用户的 DPAPI 信封保存该密钥。异盘备份复制数据库、头像和 DPAPI 信封；原 Windows 用户环境不存在时，旧信封无法解封。详见 proposal.md 的动机和 `docs/数据库异盘备份、导入与恢复说明.md` 的现有导入门禁。

本 Change 不改变业务字段的加密算法，也不把厂家私钥放入客户应用。它只增加一层用于灾备的密钥封装，并把现有“本地备份候选导入”扩展为“厂家响应导入”。

## Goals / Non-Goals

**Goals:**

- 支持主硬盘和 Windows 用户环境同时损坏后的跨系统恢复。
- 恢复请求只携带备份身份和加密密钥信封，会员数据库和头像继续留在门店。
- 复用现有出厂账号、本机维护门禁、候选校验、维护状态、原子替换、回滚和重启复验。
- 让厂家工具可离线运行，并能在不接触客户数据库的情况下处理最小恢复材料。
- 使新旧备份行为明确可区分，旧备份不被误报为支持跨系统恢复。

**Non-Goals:**

- 不实现在线厂家服务器、远程桌面或自动联网授权。
- 不把厂家私钥、门店数据密钥或恢复码打包到客户应用。
- 不改变日常备份频率、物理磁盘选择、SQLite 并发策略和业务权限模型。
- 不为已经生成且没有厂家恢复信封的旧备份凭空补造跨系统恢复能力。

## Decisions

### 1. 使用非对称厂家恢复封装，不使用统一厂家密钥直接加密业务字段

每个门店继续生成独立的 `K_store`。正式备份生成时，应用内置的厂家恢复公钥只封装 `K_store`，形成 `factory-key-envelope`；厂家离线工具持有对应私钥。备份中的业务字段仍由 `K_store` 加密，数据库文件无需重新加密。

采用公钥而不是把统一 AES 厂家密钥放进应用，是因为备份生成必须在客户机器完成，而私钥只能留在厂家环境。恢复公钥可以随应用发布，按 `recoveryKeyId` 版本化；厂家私钥与激活签名私钥分离。

备份元数据增加恢复信封格式、恢复公钥版本、`keyId`、实例身份、revision、数据库摘要和头像清单摘要。恢复信封只保护 32 字节门店数据密钥，不写入会员明文。

### 2. 用新系统临时密钥对绑定恢复响应

新系统生成一次性临时 RSA 密钥对（Node/Electron 与 Java 均使用系统标准密码能力），只把公钥写入 `recovery-request.json`。私钥保存在新系统用户数据目录的临时恢复会话中，并使用当前 Windows DPAPI 保护；成功、取消、过期或重启恢复后删除。

请求绑定以下不可变信息：请求编号、备份实例身份、`keyId`、revision、数据库/元数据摘要、临时公钥、创建时间和过期时间。厂家工具使用恢复私钥解开 `factory-key-envelope` 后，只能用该请求的临时公钥重新封装，生成最小化的 `recovery-response.json`。响应不重复携带请求已有的实例、revision、`keyId` 和临时公钥。

这样厂家不需要收到 `platform.db` 或头像目录；新系统也不会收到厂家的长期私钥。若请求文件被复制，因缺少本地临时私钥和请求绑定，不能单独完成导入。

### 3. 将恢复分为“请求生成”和“响应导入”两个明确阶段

会员管理端在登录后的“数据库备份/恢复”区域增加两个阶段：

1. 选择本地备份并生成请求，展示需要发送给厂家的文件清单和有效期；
2. 选择厂家响应和原备份，预校验通过后显示版本、最后修改时间、实例身份、会员数量和响应编号，确认后执行导入。

启动检查窗口仍不提供恢复入口，避免未登录状态下暴露备份内容或让客户误操作。请求生成和响应导入都由后端再次验证出厂账号、本机访问和当前维护状态，不能只依赖按钮隐藏。

### 4. 复用现有导入替换链路，先重封装密钥再原子替换

响应导入成功解封 `K_store` 后，后端先在临时位置生成当前 Windows 用户可用的新 DPAPI `data-key.dpapi`，并用该密钥验证候选数据库中的关键密文和头像清单。随后沿用现有导入流程：停止持久化写入、保存 `pre-import` 回滚副本、同卷 staging、SHA-256 复核、原子替换数据库/头像/密钥信封、重启后复验。

数据库和头像的密文不变，因此恢复耗时主要与文件复制和完整性检查相关，而不是逐字段重新加密。任何阶段失败都不得留下只有数据库或只有密钥信封的半套状态。

### 5. 厂家工具保持最小输入和最小输出

厂家工具输入为恢复请求公钥、请求绑定信息和备份中的 `factory-key-envelope`；工具不要求数据库文件。工具在内存中短暂持有 `K_store`，不得写入日志、临时明文文件或标准输出，只输出绑定请求编号的最小响应包。RSA-OAEP 解密失败即视为响应密文被篡改或材料不匹配，不再额外维护响应签名。

若厂家需要人工核验，可由工具读取元数据摘要和版本信息，但不读取会员明文。工具离线运行，私钥存放在厂家维护环境，响应可通过 U 盘或其他受控渠道返回门店。

### 6. 旧备份和失败材料采用明确的兼容策略

没有 `factory-key-envelope` 的备份继续支持原 Windows 用户环境下的 DPAPI 导入，但在新系统中生成恢复请求时明确拒绝。恢复响应过期、重复使用、请求/备份不匹配或 RSA-OAEP 密文校验失败时，系统只报告可操作原因，不覆盖当前主库，也不移动或删除原备份。

测试使用专用厂家临时公私钥、临时恢复会话和 `TEST` 元数据；不得读取正式厂家私钥或写入正式备份目录。

## Risks / Trade-offs

- [厂家恢复私钥泄露会使带恢复信封的门店数据密钥可被解封] → 私钥不进客户包、不进 Git，存放在厂家受控环境；恢复密钥与激活签名密钥分离并支持 `recoveryKeyId` 轮换。
- [客户丢失恢复请求会话的临时私钥] → 请求设置有效期并允许重新生成；旧请求自动失效，不影响原备份。
- [客户误把数据库文件发送给厂家] → UI 和中文说明只导出请求与密钥信封清单，并在发送提示中明确无需发送 `platform.db` 和头像目录。
- [旧备份缺少恢复信封] → 生成请求前明确检测并提示只能保留原 Windows 环境恢复；备份升级后才开始具备跨系统恢复能力。
- [恢复响应在导入中途断电] → 复用现有维护日志、回滚副本和启动恢复；增加阶段性强制终止测试。
- [厂家工具与应用版本不兼容] → 响应携带格式版本、应用兼容范围和 `keyId`；客户端在替换前完成版本与实例校验。
- [临时公私钥和恢复文件被复制] → 私钥使用 DPAPI 临时保护，响应绑定请求编号、实例身份和有效期，成功后立即删除会话材料。

## Migration Plan

1. 发布包含恢复公钥和新备份元数据格式的会员管理端及厂家离线工具；正式版本首次启动不修改旧数据库和旧备份。
2. 下一次成功备份时写入厂家恢复信封；旧 `latest` 在成功生成新格式备份前仍按原规则运行。
3. 在新系统中选择带恢复信封的备份生成恢复请求，厂家返回响应后执行一次完整导入验收。
4. 恢复成功后保留导入前回滚副本和原始备份，直到门店确认会员、账号、手环和记录正常；再按既有历史清理策略处理。
5. 若发布后发现响应格式或校验问题，回滚客户端代码即可；已有数据库和旧 DPAPI 备份仍按旧流程可用，不删除恢复信封或原备份。

## Open Questions

- 厂家恢复响应的实际交付渠道（邮件、U 盘或厂家现场工具）可在实现阶段根据门店流程确定，不改变请求/响应文件契约。

## 消融记录

本轮消融移除了两类重复设计：响应不再复制请求已经绑定的实例、revision、`keyId` 和临时公钥，也不再增加厂商响应签名。响应只保留格式、请求编号、RSA-OAEP 封装密文和过期时间；会话中的原请求负责绑定备份，OAEP 解密负责密文完整性。一次性会话、DPAPI 临时私钥、备份摘要、数据库校验、原子导入和回滚仍保留，因为它们分别承担重放防护、跨 Windows 传递、备份一致性和故障安全职责。
