## Context

会员管理端当前使用 Spring JDBC、Hikari 和 xerial SQLite JDBC。所有 HTTP 请求可以并行进入，而 Hikari 默认允许多个连接；业务方法普遍采用“读取当前状态后在事务内写入”的方式。SQLite 同一时刻只能有一个写者，当前配置没有显式统一锁等待和连接池规模，因此并发充时会直接冒出 HTTP 500。

数据库在线备份通过同一个 `DataSource` 获取连接，数据库导入和检查也依赖现有 JDBC URL 的文件路径语义。方案必须保留这些行为，并兼容正式库、开发桌面版共用库以及自动测试临时库。

## Goals / Non-Goals

**Goals:**

- 以最少生产代码消除普通门店并发量下的 SQLite 写锁 500。
- 让锁等待有明确上限，并让真正超时的锁竞争具有稳定错误码和中文提示。
- 用真实 SQLite 文件和现有多点并发工具证明业务数据正确，而不只断言配置值。
- 保持备份、导入、重启和现有 API 成功响应兼容。

**Non-Goals:**

- 不更换 PostgreSQL/MySQL，不增加消息队列或分布式锁。
- 不建立通用 Repository、命令总线、自建线程池或业务写入队列。
- 不在自助注册端、游戏端或测试代理中增加自动重试。
- 不借此重写现有事务和业务状态机；只有测试证明持锁过长时才做局部事务收紧。

## Decisions

### 1. 主业务数据源只保留一个池连接

通过 Hikari 配置把 SQLite 主数据源的最大池大小固定为 1。并发 HTTP 请求仍由 Web 线程接收，但取得数据库连接的事务会在连接池处有序等待，因此应用内部不会同时产生两个 SQLite 写事务。现有事务边界和回滚语义继续由 Spring 管理，备份也复用同一连接池并自然排队。

这比自建写队列更小，也避免漏掉某个新写接口；相比保留多个连接只依赖 WAL 和 `busy_timeout`，它不会遇到“事务先读后升级为写事务”时的竞争窗口。代价是读取也经过单连接，但当前是小门店单机数据库，先以正确性为首要目标，并在并发验收报告中观察延迟。

### 2. 显式设置 WAL、有限 `busy_timeout` 和 IMMEDIATE 事务

使用 Hikari 传给 SQLite JDBC 的数据源属性统一设置 WAL、可配置的 `busy_timeout` 和 `IMMEDIATE` 事务模式，不把查询参数拼进 JDBC 文件路径，避免破坏备份和导入代码对数据库路径的解析。启动测试必须读取实际 PRAGMA 和驱动事务模式，证明文件数据库已生效；内存数据库允许使用 SQLite 自身支持的日志模式，但仍要验证锁等待配置。

写接口普遍先读状态再写入；SQLite 延迟事务在这个升级点可能不经过锁等待便返回 BUSY。因此事务在开始时就以 `IMMEDIATE` 取得写入资格，使短暂外部写锁能够按 `busy_timeout` 等待。池大小 1 用于处理应用内部并发。暂不改变 `synchronous`、自动提交或其他耐久性参数，避免把并发修复扩大为断电策略变更。

### 3. 只识别 SQLite BUSY/LOCKED 根因

在现有 API 异常处理边界增加一个很小的 SQLite 锁识别逻辑：遍历异常 cause，只在 SQLite 错误码为 `BUSY` 或 `LOCKED` 时返回 HTTP 503、`DATABASE_BUSY` 和中文排查提示。若 `BEGIN IMMEDIATE` 因超时失败，则软淘汰这条池连接，避免 SQLite 驱动残留的事务状态影响下一次请求。约束冲突、SQL 错误、磁盘异常等继续走原有分类，不能被宽泛的 `DataAccessException` 捕获后统一伪装成数据库繁忙。

不做服务端业务重放。锁等待结束后，事务要么正常提交，要么整体回滚并返回明确失败，因此不会引入重复充值或重复积分的新路径。

### 4. 测试分为配置、受控锁和真实业务并发三层

- 配置测试验证实际连接的 PRAGMA 和 Hikari 池大小，不只检查 YAML 文本。
- 受控锁测试使用第二个 SQLite 连接持有写锁，验证短锁等待后成功、长锁得到 `DATABASE_BUSY`，并核对失败事务无部分数据。
- 业务并发测试通过真实 HTTP/真实临时 SQLite 同时运行多组注册和游戏流程，逐项核对数量、唯一性、绑定、游戏记录和积分。

最后重新运行现有打包版多点并发 smoke。客户端不重试，原来的并发规模不降低；只有报告零差异、零非预期 5xx、零 SQLite 锁日志才能勾选完成。

## Risks / Trade-offs

- [单连接使读请求也排队，峰值延迟可能增加] → 保持事务短小，通过 p95/p99 和请求超时验收；只有测量证明无法接受时才讨论读写数据源分离。
- [外部工具长期锁住数据库仍会失败] → 有限等待后返回 `DATABASE_BUSY`，明确提示检查是否有其他程序占用，避免无限挂起。
- [WAL 会在数据库旁生成 `-wal` 和 `-shm` 文件] → 继续使用 SQLite 在线备份 API，不直接复制活跃数据库文件；增加备份并发回归。
- [某个现有事务持锁时间过长] → 由并发测试和慢请求数据定位，只局部缩短该事务，不预先引入全局抽象。

## Migration Plan

1. 先增加失败复现测试，保留当前并发充时会失败的证据。
2. 上线数据源连接池、WAL、锁等待和错误映射配置，再运行全部服务端回归。
3. 使用旧数据库副本验证首次启动、读写、在线备份、关闭及再次启动。
4. 重新构建会员管理端，并执行双代理 smoke；通过后再执行正式 load。
5. 若出现兼容问题，回滚应用版本即可；本 Change 不修改表结构，旧版本仍能读取同一数据库。正常关闭应用后可由 SQLite 自行检查点，不手工删除 `-wal` 或 `-shm` 文件。
