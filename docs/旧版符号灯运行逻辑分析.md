# 旧版符号灯运行逻辑

分析日期：2026-10-09。依据本机旧版前端打包脚本和反编译 Java 源码；没有连接真实灯具验收。后续新版移植状态见下文。

## 结论

旧版通用玩法中的外围灯是一套“定时按压、避免受伤”机制，不是普通蓝色地砖得分块。显示数字的是方形符号灯，接受调试点击的是配套圆形灯。超时扣的是生命值，不是游戏得分或会员积分。

## 保存布局为什么会出现在调试界面

1. 布局保存在 `game.common_config.pixelLightWiring`，含启用状态、控制器、两个端口、四墙灯数、起点和方向。
2. 保存游戏后旧 `GameController` 清除布局缓存，下一次读取按保存配置重新生成布局。
3. `WSResponseFactory` 将地砖 RGB、方形符号灯 `pixelLights`、圆形灯 `circleLights` 一起发给前端，外围灯按四面墙分别排列。
4. 旧前端 `118.js` 的 KonvaDisplay 在布局打开时绘制方形灯和圆形灯。圆形灯注册鼠标事件，发送 `c-mousedown`，附 `controlIdx/port/index`；随后自动发送 `c-mouseup`。
5. `DefaultEndpoint` 将此模拟输入交给 `_onCircleDown`，与普通地砖 `mousedown(x,y)` 是不同入口。方形符号灯在此组件中没有对应的按下事件。

仅布局打开、灯数非零可提供外围显示；运行倒计时还需要该关卡 `option.pixelLightType = 1` 和 `countdownMin/countdownMax`。

## 通用玩法每个灯位的运行规则

| 状态或操作 | 显示 | 业务效果 |
| --- | --- | --- |
| 各灯独立倒计时，每秒减 1 | 符号灯蓝色数字、圆灯蓝色 | 无加分或扣分 |
| 点击蓝色圆灯 | 符号灯和圆灯短暂变绿；倒计时设为 `countdownMax + 1` | 播放得分音效，但没有调用加分方法 |
| 下一次定时刷新 | 继续显示蓝色倒计时 | 再次等待按压 |
| 没及时点击，倒计时变为 0 | 符号灯与圆灯黄色 | `injuredWithoutAnimation(1)`，开启生命限制时扣 1 生命，播放受伤音效 |
| 超时后约 2 秒 | 倒计时恢复到最大值，显示蓝色 | 开始下一轮 |
| 结束关卡 | 清除灯显示并取消定时器 | 不继续扣生命 |

`injuredWithoutAnimation` 在关闭生命限制时直接返回；开启时生命扣至 0 会设置游戏失败。各灯独立超时，因此同一时刻多个灯归零可能各扣一次生命。调试点击仅在有效的计分阶段处理，并有约 1 秒的同色重复输入保护；点击绿色或黄色圆灯不触发上述蓝灯重置。

例：最大倒计时为 10，按下蓝色圆灯后短暂变绿，下一次刷新回到蓝色 10，再逐秒减少。未在归零前按压就受伤；不是“按一下灯就失分”。

## 配置与旧实现的细节

- 生命限制来源：旧 `mode = 1` 使用关卡生命配置，`mode = 2` 使用全局生命配置。
- 初始倒计时按最小/最大值分配后打乱，不是所有灯同时归零。
- 旧编辑器提供 `intervalDuration`，但通用 `Level.getFrame()` 内部把间隔写死为 1，没有读取该设置。
- 定时器首次执行延迟为 0，并先减 1 再判断；最小值设为 1 时，某个灯可能一开始便进入超时。这是当前找到的旧实现细节，不代表应在新版照搬。
- 特殊玩法不能一概而论：例如 `BeachLandingHandler` 在目标阶段按中指定圆灯会调用 `tempScoring(1)`。本文主结论针对 `DefaultHandler` 的通用倒计时机制。

## 与新版的差距

调查时新版只有布局编辑、校验和外围输出/清理链路。现通过 `add-circle-light-countdown-and-debug-interaction` 移植每关圆灯倒计时、按压、生命业务和单页调试显示；规则和使用方式见 [圆灯倒计时与调试使用说明](圆灯倒计时与调试使用说明.md)。没有改普通地砖、Rank 或会员积分规则。

进一步找到旧 `run/UDPResponseFactory.java:61`：按控制器、端口、点位检查外围端口，调用 `getRGB` 替换地砖 RGB；外围数值绕过普通颜色转换。`SquareLightUtils.calcRGB` 用特殊值表示方形灯的数字/符号。尚未找到可确认的真实圆灯输入映射（已确认的 `_onCircleDown` 路径来自调试 WebSocket），也未验证新 SDK 的外围编码，故物理外围收发仍暂缓；不猜协议，不把模拟测试当作硬件验证。
