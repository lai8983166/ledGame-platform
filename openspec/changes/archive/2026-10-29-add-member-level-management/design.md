# Design

## Context

排名积分由已完成游戏汇总，剩余积分另外减兑换记录。参见 proposal.md。会员与自助查询均已有积分投影；等级应随这些投影计算，避免结算、兑换、改区间时维护第二份状态。

## Goals / Non-Goals

实现最小的等级区间 CRUD 与动态展示，不创建通用规则引擎、不复制会员等级到会员表、不改游戏端或排行榜，不提供手动定级及等级权益。

## Decisions

- schema 11 仅新增 member_levels（id、名称、最小/最大积分、创建/更新时间），加入既有备份修订追踪，不种入示例等级。升级不改会员和游戏数据。
- 非空名称最多 30 字且不重名；积分为 0 至 JavaScript 安全整数上限的整数，min<=max，两端包含，允许空档但不允许任何相交。事务内检查并写入，复用现有 SQLite 串行写入策略，防止并发重叠。
- /api/member-levels GET/POST 与 /{id} PUT/DELETE 使用现有操作员上下文；读取需登录，增改复用 OPERATIONS_VIEW（出厂/店长），删除 FACTORY_MAINTENANCE（仅出厂）。不扩展角色框架。写操作加入既有审计。
- 管理端列表的积分汇总 SQL 追加 levelName 可空字段，查询当前配置；自助查询在 profile.levelName 返回可空名称。前端将缺失或 null 显示为本地化“未定级”，保持旧字段和旧响应兼容。无逐会员额外网络请求或定时器。
- 系统设置新增“等级管理”，只有出厂/店长显示配置入口；列表、编辑和删除使用现有 DOM 弹窗、忙碌防重及焦点恢复。现有会员详情、自助信息中追加等级，不堆放说明小标题。
- 等级变更在保存配置后下一次查询/刷新立即反映，不改变账户、积分或游戏记录，也不推送到未打开的页面。

## Risks / Trade-offs

- 共享边界重叠 → 服务端与客户端均校验，接口覆盖端点和并发。
- 兑换意外降级 → 仅使用排名积分，测试扣减前后等级不变、结算后升级。
- 删除等级误改数据 → 只删除配置，确认后操作，会员落入空档为未定级。
- 既有未提交双积分内容 → 增量叠加并回归，不回退、不自动提交。

## Migration Plan

新增表与备份触发器；重复启动不改既有业务数据。隔离测试验证升级、读写和打包实操，重打管理端及自助端目录与 ZIP，游戏端无需重打。需要回退时使用升级前备份。
