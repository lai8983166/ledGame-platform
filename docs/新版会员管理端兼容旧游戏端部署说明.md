# 新版会员管理端兼容旧游戏端：部署与验收

## 网络和启动

新版会员管理端仍使用原主端口 `8090`；旧版游戏端固定请求的兼容端口为 `16668`。两个端口由同一个会员管理端后端监听，并使用同一份会员数据库。

在会员管理端所在 Windows 机器的防火墙中允许门店局域网访问 TCP `8090` 和 `16668`。旧游戏端把注册中心地址配置为会员管理端 IP；新游戏端仍使用原来的 `8090` 配置。不要把未认证的 `16668` 端口暴露到公网。

默认监听 `16668`。特殊部署可设置环境变量 `PLATFORM_LEGACY_COMPATIBILITY_PORT` 改端口；旧游戏端也必须能配置为同一个端口。若端口已被占用，会员管理端会在启动错误中指出端口及修改方式。只有完全不需要旧游戏端时才设置 `PLATFORM_LEGACY_COMPATIBILITY_ENABLED=false`。

## 快速连接检查

在旧游戏端所在机器上执行：

```text
curl http://<会员管理端IP>:16668/dev/ping
```

成功响应应包含 `{"data":"pong"}`。较新的客户端主端口可单独检查：

```text
curl http://<会员管理端IP>:8090/api/health
```

两个检查都成功后，再依次实操：给手环充值、注册并绑定会员、旧游戏端刷卡启动、完成一局并检查会员积分和游玩记录。首次连接后，房间管理按旧游戏端的来源 IP 显示房间；房间名可在会员管理端修改。

## 能力边界

- 兼容固定请求 `GET /dev/ping` 和 `POST /dev/gameCallback` 的 `cmd=1/2/3/5`。不代理旧端任意 `/console/forward` 请求，也不实现可选 `notifyURL`。
- `cmd=5` 会逐一校验会员与手环资格；只有整批都有效才激活待启用手环。`isAdmin=true` 只是旧协议元数据，不会跳过会员、手环或计时资格校验。
- 旧协议用来源 IP 识别房间；每个旧游戏端必须有可区分的来源 IP。共享 NAT 下的多台旧端会被视为同一房间。
- `cmd=1` 每 20 秒心跳，超过 60 秒无心跳后房间显示离线。旧协议没有控制器/地砖健康、实时积分、排队和剩余游戏时间数据，因此这些状态不会被伪造。
- `cmd=3` 只上报最终积分，没有局 ID、结束原因、事件序号或可靠重试。积分按旧端最终值保存，记录会标记为“旧协议已结算，结束原因未知”。已接受回调的完全相同重放会由指纹识别，不会结算当前新局；但协议无法区分“重放”与同一房间、游戏、玩家再次产生完全相同积分的真实新局，后者也会被视为重复。此外，无法可靠关联内容不同的迟到旧回调，需通过现场验证确认旧端不会延迟或乱序发送。
- 游戏开始和结束通知是旧端的异步回调，没有重试保证；若请求发出时网络中断，需检查会员管理端记录并人工核对。后端重启后已持久化的局与参与者仍可关联，房间在线状态等下一次心跳恢复。
