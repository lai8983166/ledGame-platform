## Context

当前自然完成黄金流程由 Debug Panel 向 `/engine/game/input` 发送一次性 `GameInput(type="click")`。真实 ELC-408 输入则经过接收状态机、坐标映射、0x68 TCP 回传和 `TcpLedClient`，形成 `GameInput(type="tile", value=1|0)`。两者在 `GameRuntimeService` 汇合，但 `SimpleGameHandler` 仍识别两套输入语义：`click` 立即处理，`tile` 进入按下/抬起队列并随游戏帧处理。

得分、扣血、关卡判定、自然终止和平台结算已经共享。缺口位于共享规则之前：现有大型验收不会发现真实地砖按下/抬起时序、断线重置、TCP 接线或 `PRODUCTION` 硬件就绪分支的错误。验收 profile 还关闭了全部 LED 输出和 ELC-408，因此当前测试证明的是业务闭环，而不是生产形态的软件输入输出闭环。

本 Change 涉及 `ledGame`、`ledGame-backend` 和 `ledGame-platform`，但不要求现场物理设备，也不改变会员平台业务接口或数据库模型。

## Goals / Non-Goals

**Goals:**

- 让 Debug 和真实控制器在进入游戏规则前产生同一种地砖领域事件。
- 让 Simple Game 的得分和生命规则不再识别 Debug 专用的 `click` 分支。
- 保留真实地砖的按住、抬起、快速踩踏和输入会话重置语义。
- 通过契约测试证明 Debug、TCP/ELC 适配器的输出符合统一输入契约。
- 通过同夹具一致性测试证明不同输入来源产生相同游戏结果。
- 在无真实硬件环境中执行一个 `PRODUCTION` 运行模式的生产形态场景，覆盖就绪边界、LED TCP 输出、0x68 输入回传、自然结束和结算。
- 在中文测试报告和说明中明确自动化覆盖与现场硬件验收的边界。

**Non-Goals:**

- 在自动化环境中认证真实 ELC-408 控制器、地砖、电气、UDP 网络、灯光颜色或安装布线。
- 重写游戏引擎、游戏配置格式、得分策略、排队或会员结算协议。
- 将强制关卡成功、跳关、重试或 `End Game` 变成正常游戏输入。
- 为测试引入 Redis、消息队列、云服务或长期运行的模拟器进程。
- 删除通用 Demo Engine 的灯光编辑 `set/release` 能力。

## Decisions

1. **在运行时边界引入规范化 `FloorInputEvent`。** 事件只表达 `DOWN`、`UP`、`RESET` 以及合法坐标，不携带 Debug、ELC-408、HTTP 或 TCP 来源信息。`GameInput` 继续作为现有 HTTP/IPC 传输 DTO；`GameRuntimeService` 负责校验和规范化，游戏规则只消费领域事件。相比让每个 `GameHandler` 继续解析字符串 `type/value`，这一边界可以避免输入来源渗入规则层，也能集中处理非法值和兼容逻辑。

2. **Debug 正常交互直接发送 `tile DOWN -> tile UP`。** Debug 画布和确定性“自然完成”动作均通过现有 `/engine/game/input` 端点发送两次有序事件。现有 `click` 输入只在传输规范化层保留短期兼容，并转换为同一组 `DOWN/UP`，不得继续进入 `SimpleGameHandler` 的独立规则分支。相比保留 one-shot 规则分支，这能让大型验收覆盖真实地砖使用的按键状态机。

3. **按下状态属于游戏领域，硬件防抖属于适配器。** ELC-408 状态机继续负责物理状态、坐标映射和防抖；运行时处理器负责某坐标是否仍被踩住、同一物体是否已交互以及跨帧行为。`RESET` 在输入连接断开、游戏停止和会话替换时清空活动地砖。这样既不会把硬件细节带入游戏规则，也不会把“持续踩住移动目标”的游戏语义误放到驱动层。

4. **调试覆盖与游戏行为覆盖分开命名。** `End Game`、强制关卡结果、跳关和重试继续受 `SIMULATION` 限制并使用 `/engine/game/debug/command`。它们只验证生命周期或故障恢复，不计入得分规则和自然完成覆盖。正常命中必须使用地砖输入契约并经过 `evaluateLevel()`。

5. **采用“适配器契约 + 规则一致性 + 生产形态验收”的分层测试。** 适配器测试验证 Debug 请求和 ELC/TCP 字节流生成正确的规范化事件；规则测试将同一事件序列送入同一游戏夹具并比较完整 gameplay snapshot 与 LevelOutcome；跨仓库验收验证真实 UI、IPC、HTTP、运行时、结算和队列。这比只扩大一个慢速 Playwright 场景更容易定位失败，也避免用 UI 测试穷举地砖时序。

6. **用测试拥有的双向 TCP 地砖替身覆盖 `PRODUCTION` 软件路径。** 验收进程启动一个临时 TCP 服务，接收后端输出的 LED 帧并回写生产格式的 0x68 `DOWN/UP` 数据。`GameLaunchService` 依赖一个窄的硬件就绪端口：生产实现调用 `Elc408RuntimeManager`，acceptance 实现仅在 acceptance profile 下返回与夹具匹配的就绪结果。场景仍以 `runtimeMode=PRODUCTION` 启动，从而覆盖生产分支，而不伪造真实 UDP 控制器发现。

7. **生产默认值保持 fail-closed。** 测试就绪替身只能由 acceptance profile 和显式测试配置启用；正常配置继续调用真实 ELC-408 就绪检查。缺少真实控制器时，生产启动仍必须失败并保留准备会话。不会增加可由普通 UI 打开的“跳过硬件检查”开关。

8. **输出也纳入生产形态场景，但不做像素视觉认证。** TCP 替身至少断言收到一个协议合法、尺寸匹配的 LED 帧，然后才回写输入。这样可以发现输出没有连接或尺寸不一致，但颜色准确度、刷新稳定性和物理显示仍由现场检查负责。

9. **保留一条简短现场冒烟清单。** 自动化报告必须标明“生产形态软件测试通过”而不是“硬件验收通过”。发布前现场只需验证控制器发现、地砖坐标/按下抬起、灯光输出和断线恢复等不可远程证明的项目。

## Risks / Trade-offs

- [将 Debug 改成 DOWN/UP 后暴露旧 click 测试依赖] → 先增加规范化和一致性失败测试，再迁移测试夹具；传输层暂时兼容 `click`，规则层不保留双实现。
- [快速连续 DOWN/UP 可能在引擎 tick 前到达] → 统一事件队列必须保持顺序，并保留现有“一次快速踩踏只交互一次”的回归测试。
- [测试就绪替身被误用于生产] → 通过 Spring profile、显式属性和启动断言三重限制，生产配置中不注册替身。
- [双向 TCP 替身提高验收编排复杂度] → 由现有 run-owned harness 分配端口和管理生命周期，失败时记录有限协议事件，不创建常驻服务。
- [适配器测试通过仍不能证明真实硬件] → 中文报告明确范围，并维护单独的现场冒烟清单。
- [旧客户端仍发送 `click`] → 兼容转换保留一个迁移周期并记录测试覆盖；所有仓库完成同步发布后再单独决定是否删除。

## Migration Plan

1. 先提交失败的规范化输入、适配器契约、规则一致性和生产形态验收测试。
2. 在游戏后端加入领域输入事件和规范化边界，迁移 `SimpleGameHandler`，保留 HTTP `click` 兼容转换。
3. 将 Debug Panel 正常交互和大型验收迁移为显式 `DOWN/UP`。
4. 抽取硬件就绪端口，保持生产实现不变，并加入 acceptance-only 实现与双向 TCP 替身。
5. 运行三个仓库的聚焦测试、完整测试和跨端验收，确认 Debug 与生产形态结果一致。
6. 回滚时可恢复 Debug `click` 发送和原就绪依赖；没有数据库迁移或持久数据需要回退。

## Open Questions

- 本 Change 默认保留 `/engine/game/input` 的 `click` 兼容转换，但不承诺长期支持；是否彻底删除应在所有现有调用方迁移后另行决定。
