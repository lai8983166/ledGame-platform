## Context

会员表目前只允许 `ACTIVE` 与 `FROZEN` 状态，活动手机号唯一索引仅约束 `ACTIVE` 记录。会员查询、Player Info、排行榜、绑定和游戏准入已经以 `ACTIVE` 为边界；手环绑定和游戏记录通过外键引用会员，因此物理删除会破坏历史关系或要求危险的级联清理。

会员管理端当前在手环办理页面常驻显示 UID 与分钟输入框，按 Enter 会直接调用充值接口。键盘式读卡器会连续输入数字并发送 Enter，因此新交互需要明确限定捕获窗口，且扫描完成不能等同于数据库充值完成。

## Goals / Non-Goals

**Goals:**

- 让固定测试手机号能够在两个注册入口之间反复完成“注册—删除—重新注册”。
- 保持旧会员历史数据的会员 ID 归属，同时让新会员从零开始。
- 给删除操作设置进行中手环和游戏保护，并保证事务一致性。
- 将充时改造成可取消、可重试且只有最终确认才写库的显式状态机。
- 复用真实键盘式读卡器的“数字 UID + Enter”行为，不增加硬件 SDK。

**Non-Goals:**

- 不提供隐私法规意义上的个人数据彻底擦除或历史数据匿名化。
- 不在本 Change 中实现会员冻结、恢复或已删除会员管理页面。
- 不提供批量删除会员、批量充值、退款或支付系统对接。
- 不改变自助注册端现有页面流程；它继续依赖活动会员查询结果决定注册分支。
- 不改变清除余额、解除绑定和回收手环的既有操作。

## Decisions

### 1. 使用 `deleted_at` 区分软删除，不扩展受 CHECK 约束的状态枚举

迁移为 `members` 增加可空 `deleted_at`。删除事务把 `status` 从 `ACTIVE` 更新为 `FROZEN` 并写入 `deleted_at`；普通冻结将来仍可使用 `FROZEN + deleted_at IS NULL`，删除则由 `deleted_at IS NOT NULL` 明确识别。所有活动会员判断使用 `status='ACTIVE' AND deleted_at IS NULL`。

选择该方案是因为 SQLite 无法直接修改既有 CHECK 约束，新增 `DELETED` 枚举通常需要重建会员表及其外键关系。物理删除和级联删除会丢失游戏/积分审计链；单纯复用 `FROZEN` 又无法区分删除与临时冻结。

### 2. 提供以会员 ID 为目标的事务型软删除接口

新增 `DELETE /api/members/{id}`。事务中先确认目标是活动会员，再检查该会员是否存在 `READY`/`ACTIVE` 绑定或 `RUNNING` 游戏；有进行中业务时分别返回稳定冲突码，全部通过后才写入软删除标记。接口返回被删除会员的 ID、手机号和逻辑状态，便于 UI 更新与测试断言。

删除使用不可变会员 ID，不使用手机号作为目标，避免同一手机号删除后重新注册时误操作新记录。对已删除或不存在 ID 返回稳定未找到结果，不修改任何关联记录。

### 3. 新注册保持新身份，不迁移旧历史

活动手机号唯一索引会在旧记录退出 `ACTIVE` 后释放手机号。管理端和自助端继续调用同一创建会员接口，新记录获得新 ID。积分、Player Info、绑定和游戏记录均按会员 ID 聚合，因此无需复制或清零旧行，新会员自然从零开始。

### 4. 删除入口位于会员详情的危险操作区

会员列表行继续只提供查看入口。详情抽屉底部增加“删除会员”，点击后使用应用内确认弹层展示姓名、手机号以及“手机号可重新注册、历史记录保留”的说明。取消无请求；成功后关闭抽屉并重新请求活动会员列表；冲突错误保留详情和确认上下文，指导店员先处理手环或游戏。

选择应用内弹层而不是 `window.confirm`，以便稳定测试、展示关联状态错误并保持现有视觉体系。

### 5. 充值 UI 使用独立的有限状态机

充值会话状态为：

```text
idle → scanning → checking → details → submitting → idle(success)
          ↑          │          │
          └── retry ─┘          └── error → details

scanning/details ── cancel → idle
```

页面初始只显示“手环充值”按钮。全局键盘监听器仅在 `scanning` 接受数字与 Enter；Enter 后进入只读检查，使用扫描会话版本号忽略取消后的迟到响应并阻止重复提交。未知 UID 视为可创建的新手环，`IN_STOCK` 视为可再次办理，其余状态返回扫描阶段错误并允许刷另一只手环。

进入 `details` 后停止读卡器捕获，显示只读 UID、数值输入框和现有快捷值 `[30, 45, 60, 90, 120]`。最终确认才调用既有原子充值接口。提交期间禁用确认与取消，避免无法撤销的在途写入被误认为已取消；失败返回 `details` 并保留输入以便重试。

### 6. 服务端始终是充值资格的最终裁决者

扫描后的状态检查只用于提前改善交互。扫描与确认之间手环状态可能被其他操作改变，因此现有充值接口仍必须在事务中重新校验状态；前端展示其稳定冲突结果，不根据先前检查强行判定成功。

## Risks / Trade-offs

### 7. 使用独立充值流水支撑真实收入统计

新增 `wristband_charge_records` 表，在现有充值事务完成手环写入后同步插入 UID、分钟数、固定单价 100 分、金额和充值时间。运营总览按门店时区计算当天起止 Instant，并聚合该流水表。不能直接使用 `wristbands.charged_at` 和当前 `duration_minutes`，因为清除、回收与再次充值会覆盖或清空这些字段，无法形成可信历史。

### 8. 总览分别读取统计投影与真实房间投影

新增只读 `GET /api/dashboard/overview` 返回四项数据库统计，房间继续复用 `GET /api/rooms` 和现有 `mapRoomStatus`。管理端并行读取两者，提供加载错误与手动刷新。设备健康 Card 删除；房间列表改为占据总览内容区全宽。手环管理页只调整组件布局和密度，不改变充值状态机或其他操作接口。

- [软删除仍保留姓名和手机号，不等同于隐私擦除] → UI 明确描述为运营删除/重复注册能力，彻底擦除不在本 Change 范围。
- [同一手机号会在数据库中积累多条历史会员] → 活动查询只返回一条新记录，历史按旧 ID 保留；SQLite 单店规模下增长可忽略。
- [删除检查与状态更新之间发生并发绑定] → 在同一事务中执行检查和更新，并让绑定/准入继续校验活动会员；集成测试覆盖冲突路径。
- [扫描检查后手环状态发生变化] → 最终充值接口再次校验并返回错误，前端保留详情供重试或取消。
- [全局键盘捕获影响其他输入] → 只在 `scanning` 状态安装或启用监听，离开页面、取消和组件卸载时清空缓冲并注销。

## Migration Plan

1. 以幂等迁移为 `members` 增加 `deleted_at` 可空列；现有会员保持未删除。
2. 更新活动会员查询与删除接口，并先通过真实 SQLite 集成测试。
3. 接入管理端删除确认和充值状态机，再运行管理端单元测试、类型检查与构建。
4. 运行核心流程和端到端测试，确认未删除会员的注册、绑定、游戏和积分行为不变。
5. 回滚旧版本时新增列会被忽略；已软删除记录保持 `FROZEN`，不会被旧版本误识别为活动会员。
