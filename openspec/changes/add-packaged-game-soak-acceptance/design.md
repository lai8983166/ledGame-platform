## Context

现有 multipoint-concurrency 以接口负载和核账为主，不运行游戏 UI。游戏端已有 `mode=game`/`debug` 与 `entryMethod=touch`，游戏模式向导顺序为人数、游戏轮播、起始关卡、启动倒计时。游戏自然结束到 STOPPED，结果页 `game-return-idle` 按钮显式回到 IDLE，没有自动返回待机逻辑。配置步骤有 20 秒无操作超时。

此前 `unify-debug-production-floor-input` 已统一 DOWN/UP 输入，并提供 acceptance-only 硬件就绪替身及双向 TCP 测试思路。本次应先复用，不另造游戏规则。当前真实 ELC408 发现结果数量不能当作配置控制器数量的必然等值条件。

## Goals / Non-Goals

**Goals:** 用打包程序、真实按钮和可复核日志回答：指定游戏能否循环自然结束、程序是否退出/卡死、内存是否持续增长、可观测的真实通信是否异常。无人踩踏正常计时，有人踩踏不打断编排，模拟注入独立可选。

**Non-Goals:** 启动会员管理端/自助注册端、中心数据库/备份/激活准备、三端联动、通过界面强行结束游戏、自动改游戏时长、反复注册会员/充时、全量原始报文长期记录、极限并发压测、断电断网故障注入、承诺物理地砖/网络根因可由程序确定、给测试工具另做 GUI。触屏无会员运行不以会员积分缺失判失败。

## Decisions

### 1. 独立测试模块与最小配置

在平台仓库新增 `game-soak-acceptance`，使用 Playwright 和独立便携命令行入口。复用现有进程/目录所有权能力，但不抽取通用测试框架，不改变并发工具的数据结构。现场工具自带所需运行时和自动化依赖；不要求安装 pnpm、Node.js、Java 开发环境。不单独下载浏览器来代替 Electron；通过打包应用连接真实窗口。

配置包含：

| 字段 | 约定 |
| --- | --- |
| runId、outputRoot | 唯一运行身份和输出目录，不复用已有运行目录 |
| gameExecutable | 游戏端打包 exe 路径，其自带后端随游戏端正常拉起；不要求其他两端或中心地址 |
| games | 非空有序数组，每项为实际数据库 gameId、playerCount、startLevelIndex；不按名称/屏幕位置匹配，第一版拒绝重复 ID |
| durationHours | 默认 18；允许短时自测，报告写真实时长，不将短测当 18 小时通过 |
| hardwareMode | `real` 或 `simulated`，正式硬件验收必须 real |
| floor | 本次实际尺寸和已有 wiring/conf 来源，可为 8×8，不重写配置格式 |
| simulatedInputEnabled | 默认 false，仅开放受控注入，不自动生成踩踏脚本 |
| limits | 操作/启动/结算超时、内存绝对上限和增长阈值；固定在开测前，随报告保存 |

增加只读预检/列表输出，列出实际 ID、名称、类型、可见性和有效总时长，方便填配置。提交一个不含虚构可运行 ID 的模板，要求用户从实际列表填入。重建数据库后的 ID 变化会明确失败，而不是同名替换。每局开始前重新核对可见 ID 与内容指纹，运行中游戏配置变化停止验收，避免悄悄换测对象。

预检确认每个游戏支持当前向导、起始关卡存在、人数合法、全局时长有限且实际生效（Rank 按其整局时长规则解析）。预检不改游戏源库、不做 DB 重置，不访问中心库。

独立运行不连接会员管理端：隔离配置复用游戏后端现有 `ledgame.member-platform.room-connection-enabled=false` 关闭房间重连，触屏会话不创建平台会员准入/结算记录。预检和短测须证明在会员平台不存在时仍能完成启动、运行和自然结束；若存在未发现的强依赖，应记录为游戏端独立运行缺口并在游戏仓库修复，不通过启动假中心或其他两端绕过。关闭房间联动只影响本次隔离配置，不改变正常安装设置或掩盖控制器错误。

### 2. 固定游戏模式，所有业务导航走点击

工具拥有的隔离配置设 `mode=game`、`entryMethod=touch`；逐局记录运行状态证明没有变成 debug 或 SIMULATION 游戏运行模式。只读 API 可用于预检和证据，不能替代 UI 选择、开局、结束和返回。UI 点击用稳定 data-testid；轮播只点真实可见项目/左右箭头，确认目标已居中后点下一步，不修改 Vue 内部状态或隐藏 DOM。

| 步骤 | 点击/等待 |
| --- | --- |
| 启动 | 仅启动游戏端，等待自有后端/主窗口就绪，在游戏主窗口点击进入游戏 |
| 待机 | 点击 `game-touch-idle`，等待 PREPARING 的 players 步骤 |
| 人数 | 点击 `game-player-count-N` → `game-player-next` |
| 游戏 | 轮播到配置的 ID，确认当前项目 → `game-game-next` |
| 关卡 | 点击 `game-level-index` → `game-start` |
| 游玩 | 确认 STARTING/RUNNING，等待自然结束；允许观察不到很短的中间状态，但权威生命周期必须完整 |
| 结束 | 核对当前 session/gameId 和自然终止原因，再点 `game-return-idle`；确认 IDLE 后推进配置索引 |

为虚拟化轮播补稳定方向按钮和当前游戏 ID 观测点；主要选择器已在 Touch 页面存在。每次点击均等待对应状态，准备步骤必须在 20 秒内推进。自动回退到待机、点击超时、队列接续或后台游戏被改动均是偏离计划，不计作完成一局。测试开始要求没有已有活动局和排队，本次不注入队列。

### 3. 时间边界与失败处理

从第一局 RUNNING 起以单调时钟计满 18 小时，包含正常局间操作时间，另报累计 RUNNING 时长和每款游戏局数。满时不开始新局，当前局允许按有限全局时长自然收尾，收尾不算额外测试覆盖；最长收尾为该局剩余总时长加预先配置的结算宽限。开测前预估至少能遍历一次全部列表，否则拒绝正式验收。

自然结束采用实际后端终止原因枚举的白名单，实施时先核对各玩法，不只看 STOPPED。正常失败/生命耗尽也可自然结束，不要求无人工输入时一定获胜。每局必须有开局和结束证据；超时不点 End Game 补成功。遇到进程异常退出、界面步骤卡死或非自然中止，保存截图/状态/日志并结束本轮为失败；不自动重启掩盖故障。用户主动中断标记“未完成”。关闭自己启动的进程是测试清理事件，与测试期闪退区分；不终止用户已有进程。

### 4. 无硬件开发与现场模式

simulated 使用独立运行目录、显式验收配置和已有生产形态就绪/输出替身，仍走游戏模式 UI 与 PRODUCTION 生命周期；不要改成 DebugPanel，也不要虚构已连接控制器。先以打包 Java 后端验证现有 acceptance 机制的可用性，再补最小配置传递。模拟输出至少验证收到有效帧，不伪造真实 UDP 收发统计。普通游戏配置没有跳过硬件就绪入口。

real 必须连接实际 SDK/控制器，复用真实配置和就绪检查，不自动回退 simulated。配置控制器数量与发现数分开记录，不重新引入“必须搜到全部控制器才允许运行”的错误约束。测试样本是否存在真实踩踏另记，用户没人踩不构成 UI 循环失败。

### 5. 可选模拟踩踏接口

优先在现有输入端点前加薄验收适配，不新建模拟游戏引擎。仅在显式开关打开且请求来自本机、runId/当前会话匹配时接受坐标和 DOWN/UP；校验范围、顺序、请求大小及可接受速率。无需提供得分、过关或强制结束指令。正常运行默认关闭，结束后撤销注入会话，过期请求拒绝。

来源标记放在输入适配与日志层，不进入玩法规则。真实按住集合与模拟按住集合分开，向统一规则层输出合并后的状态变化；模拟 UP/RESET 不能释放仍被真实踩住的格子。会话结束/替换清理旧会话输入，不把迟到 UP 注入下一局；注入测试覆盖同坐标重叠和快速 DOWN/UP。注入不会经过真实网络/控制器，所以只记模拟事件，不增加硬件接收成功次数。

### 6. 监测与报告

每 10 秒记录游戏端进程树的 PID+创建时间、角色、私有内存和工作集，捕获新生/退出子进程。游戏主进程、自有 Java、窗口渲染进程异常退出单独判断；正常短暂子进程退出不一概算闪退。对游戏主窗口、Touch 及实际启用的副屏做只读响应探测，不要求新增副屏或连接第二块显示器，不在游戏中插入会改变状态的点击。测试器自身内存单独记录，避免采集器泄漏被归因于产品。

内存报告至少给出时间曲线、峰值、预热后分窗口中位数及增长率，汇总游戏端总占用，并区分 Electron、自有 Java 和子进程证据；不能简单用末值减初值定泄漏。正式通过需要开测前声明的内存上限/增长阈值，未设阈值只报告观察结果并标记“未判定”，不能默认通过。预热默认 10 分钟，短于趋势窗口的自测不判长期内存稳定。

真实通信在实际发送/接收/解析处计数，不靠 UI 动画猜测：发送尝试/失败、收到的数据包、解析拒绝、现有协议可验证的校验失败、连接变化；仅在协议具有可靠对应字段时记录应答超时/序号异常，否则写“不支持判定”。零接收可能是无人踩踏或协议不周期回传，不擅自认定断网。缺失指标、采样中断和计数重置明确记录，不能用零补齐。

按 10 秒区间输出汇总并保留有限异常样本，限制日志/截图总量；不全程录屏、开启全量 trace 或持有 18 小时请求数组。错误标注阶段、方向、session、游戏 ID、时间和实际原因；不确定物理根因时给出检查建议，不直接声称是硬件/网络导致或软件必然无责。

报告分软件可用性、内存、真实通信、模拟输入四部分。软件通过要求完整时长、每款游戏覆盖、无异常退出/卡死/非预期中止、证据连续；内存按预声明阈值；通信按可测错误为零和所需路径有观测证据判断。simulated 的真实硬件栏为“未验证”；real 无回传样本不能宣称输入链路已通过。总报告可为通过/失败/未完成/部分未验证，不把未知转成通过。

## Risks / Trade-offs

- [无硬件不等于物理验收] → 两种模式在配置和结果中固定区分，代码测试通过不勾选真实 18 小时项。
- [API 能读到游戏但 UI 不可见] → 以独立运行时的实际可见轮播列表预检，不跳过或为了改变可见性拉起会员管理端。
- [真实踩踏改变得分/提前自然结束] → 不预设固定积分或局数；核对对应会话与自然终止，不重用并发工具精确积分预期。
- [监控或硬盘写满影响运行] → 采样有界、日志限额、磁盘不足明确停止并保留已写证据。
- [用户正常游戏库被烤机污染] → 仅隔离游戏端用户目录，游戏库/配置复制已确认输入且来源只读；不接触其他两端的库、备份或授权。
- [跨仓库实施超范围] → 本 Change 作为主验收规划；平台实现其工具，游戏端/后端改动在各自仓库建立对应实施记录并运行本仓库测试后联调。

## Migration Plan

先做配置/证据契约和失败测试，再建立无硬件、无会员平台的游戏端短循环；补注入与通信采集后打包便携工具，最后在真实硬件环境实跑 18 小时。正常游戏业务无数据库迁移，默认不开注入；回退测试工具不会改变正常游戏结束/返回交互。
