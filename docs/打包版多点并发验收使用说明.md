# 打包版多点并发验收使用说明

这套工具验证“两台压力机模拟多个注册端和游戏端并发调用会员管理端时，是否丢会员、错绑手环、漏记录、算错积分或发生执行积压”。操作的是打包版会员管理端，使用完全隔离的测试数据库。

## 选择时长

| 档位 | 持续时间 | 每台压力机 | 用途 |
|---|---|---|---|
| `quick` | 5 分钟 | 3 个注册端 + 6 个游戏端 | 先验证连接与完整流程 |
| `standard` | 30 分钟 | 同上 | 常规验收 |
| `soak` | 2 小时 | 同上 | 持续运行验收 |
| `overnight` | 12 小时 | 同上 | 通宵持续运行验收 |

两台合计模拟 6 个注册端、12 个游戏端，穿插管理查询。设备独立运行，包含随机到店间隔、操作等待、集中到店、新老会员和同手环重复游戏；每局模拟游玩 30～180 秒后自然结算。不是所有请求同一节拍发送，也不是极限吞吐压测。

只选择档位，不需要逐个调并发参数。相同 runId、agentId 和档位可生成相同计划；换 runId 会换一套随机场景。

## 准备

- A、B、C 三台 Windows 电脑连接同一局域网，防火墙允许测试端口（默认 `18090`）。
- A 放置本次更新后的打包版会员管理端和本工具；B、C 各复制一份本工具。旧会员管理端缺少精确查询筛选，不能用于本次长时核账。
- A 修改 `config\center.json`：填写会员管理端 exe 路径、A 的局域网 IP 和唯一 runId。不要改安全确认值。
- 正常会员管理端必须先关闭，默认正式端口 `8090` 也必须离线。

## 执行

1. A 运行 `center.cmd`。看到健康检查通过后，将生成的 `runs\<runId>\connection.json` 复制到 B、C 工具根目录。
2. 可先在任意一台机器预览两节点合计预期：`agent.cmd --connection connection.json --preview-only true --profile quick`。预览不发任何网络请求，只保存计划和中文预览。
3. B 执行：`agent.cmd --connection connection.json --agent-id B --profile quick`。
4. C 尽量同时执行：`agent.cmd --connection connection.json --agent-id C --profile quick`。两台必须使用相同档位。也可以用 `--config config\agent-quick.json` 选择模板。
5. 将 B、C 的 `runs\<runId>\B`、`runs\<runId>\C` 目录复制回 A。
6. A 执行：`verify.cmd --connection runs\<runId>\connection.json --agent runs\<runId>\B --agent runs\<runId>\C --output runs\<runId>\report`。
7. 打开 `report\验收报告.md`。只有整体结论为“通过”、数据零差异、执行节奏通过且两机实际有重叠，才算通过。
8. 正常关闭测试会员管理端，再按平时方式启动会员管理端；正式数据库不会被测试数据替换。

quick 通过后，正常关闭测试实例，改一个新 runId 重新运行 center；在上述预览和两个 agent 命令中统一将 `quick` 换成 `standard`、`soak` 或 `overnight`。不要在旧 runId 下反复写入，也不要只改一台压力机的档位。

12 小时档示例（B 节点，C 节点改为 `--agent-id C`）：

```bat
agent.cmd --connection connection.json --preview-only true --profile overnight
agent.cmd --connection connection.json --agent-id B --profile overnight
```

也可使用 `--config config\agent-overnight.json`。通宵运行前接通电源，关闭三台机器的自动睡眠／休眠，避免系统更新自动重启，留足磁盘空间；仅熄屏不影响脚本运行。12 小时指负载阶段，结束后复制结果及核账还需要额外时间。档位和离线测试通过不代表已经完成真实 12 小时实机验收。

## 预览与验收看什么

- **运行前**：`执行预览.md` 列出本次计划的新增会员、新增手环、充值记录、绑定记录、结算局数和累计积分。老会员与重复游玩的手环按身份去重；这些预期不会因为运行变慢或请求失败而缩水。
- **运行中**：每 30 秒打印已执行请求、到点待执行数量和正在请求数量。完整原计划在 `plan.json`，每个业务流程的请求结果逐条写入 `results.jsonl`。
- **运行后**：报告逐项核对关联和数值，再列出“预期／实际／差异”，不是只看 HTTP 200 或总数。一次自然结算必须对应一条正确会话，会员积分必须等于其全部计划游戏积分之和。
- **时间不是文件大小**：不同 runId 的数据量略有不同，但本轮记录数量可以提前精确计算。SQLite、WAL、日志和备份文件的 MB/GB 受存储布局影响，不作为精确验收目标。

## 如何发现积压

每个请求保存三个指标：原定发送时间、实际发送时间、请求耗时。时间差用压力机本地单调时钟计算，不依赖三机时钟完全一致。

- **启动延迟**＝实际发送时间－原定发送时间。调度不会因为前一请求慢就把后续计划整体后移；因此排队会留下延迟证据。
- **到点待执行**＝已经到计划时间、却还没发出的请求。不计未来请求，也不计已经发出仍在等待响应的请求。每秒采样，并在请求开始时记录峰值。
- **请求耗时**包含网络和服务器处理时间。单凭这个值不能认定 SQLite 堵塞；启动延迟也可能来自压力机负载，报告不猜物理根因。

本版执行节奏标准：启动延迟 **p95 ≤ 2 秒**，无跳过步骤、无截止未执行步骤。原计划时长后最多收尾 30 秒；到截止不再发新请求，已经发出的请求最多再等其 5 秒超时。未完成或超限不得判整体通过，即使最终数据全部补齐。请求失败、超时、数据库锁错误也不能通过。

逐请求证据在 `results.jsonl`；管理查询及逐秒积压曲线在 `summary.json` 的 `queryResults`、`schedule.samples`。核账器会重建计划并根据逐请求证据复算执行节奏，不能只靠摘要的“通过”标记。

## 数据隔离与边界

- 测试数据和测试备份保留在本次 runId 目录，便于复核；工具不会自动删除，也不会自动结束任何程序。
- 若提示正常平台在线、端口占用、程序不存在或目录不可写，先按提示处理，工具不会换随机端口绕过问题。
- `TEST` 备份 root override 只用于隔离测试数据，不代表完成了真实双硬盘备份验收。
- 此测试绕过 UI，覆盖中心公开 API 和 SQLite 并发写入；不覆盖自助注册端/游戏端界面、游戏本地后端、房间 IP、控制器、地砖或真实刷卡器。
- 为比较两机重叠区间，应让 Windows 自动校时开启；每台机器自己的启动延迟不受跨机时钟偏差影响。
- 旧 `smoke` / `load` 配置仅为兼容原短流程保留，不用于新的定时随机验收。

## 开发与发布

在 `ledGame-platform` 仓库运行 `pnpm portable:multipoint-concurrency`，产物位于 `release/multipoint-concurrency`，包含 Node 运行时，无需客户安装开发环境。

自动测试：`pnpm test:multipoint-concurrency`。打包版本机双节点 5 分钟验收：先运行 `pnpm portable:member-admin:dir`，再运行 `pnpm test:multipoint-concurrency:packaged`。后者使用隔离目录和空闲端口，结束时只正常关闭自己拉起的实例，不关闭其他 Java/Electron 进程；本机结果不能替代三台实体机器的局域网验收。
