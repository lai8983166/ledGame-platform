## Why

门店仍可能运行旧版游戏端，而新版会员管理端当前只提供新版游戏端使用的 API。需要让旧游戏端的手环校验、游戏开始、最终积分上报和在线探测接入新版会员及游玩记录系统，同时继续复用新版已有的资格校验、积分查询和排行榜能力。

## What Changes

- 新增旧版游戏端固定 HTTP 协议兼容入口：`POST /dev/gameCallback`（`cmd=1/5/2/3`）和 `GET /dev/ping`，监听旧版固定使用的 16668 端口。
- 将 `cmd=5` 的手环批量校验转换为新版会员与手环资格校验／激活，并返回旧端可解析的 `code/msg/data`、嵌套数组和 `Token` 字段。
- 将 `cmd=2/3` 转换为新版多人游玩记录；按旧端逐玩家上报的最终积分保存，不重新套用新版玩法计分策略；以独立的旧协议结算状态表示“已收到结算但结束原因未知”，并计入会员总积分与排行榜。
- 将旧端 `cmd=1` 心跳以及游戏开始／结束通知投影为按游戏端来源 IP 识别的房间在线和当前游戏状态。旧协议未提供的实时分数、排队状态、控制器／地砖健康状态不伪造。
- 会员管理端房间卡片展示旧端已知玩家，但不把缺失的实时积分显示为 0；游玩记录明确标记旧协议未提供结束原因。
- 新增对固定协议的集成测试；保持新版游戏端 API 和现有行为不变。
- 不实现旧端动态 `/console/forward` 的任意路径代理，也不实现可选 `notifyURL` 回调；二者不是固定的旧游戏端到会员管理端核心协议。

## Capabilities

### New Capabilities

- `legacy-game-client-compatibility`: 接收并转换旧游戏端固定 HTTP 协议，提供旧格式响应、旧房间状态投影及可追溯的旧积分结算。

### Modified Capabilities

- `game-play-records`: 允许旧端会话使用服务端生成的关联 ID，并明确记录结束原因未知的旧积分结算。
- `player-info-query`: 将旧端已结算积分纳入会员积分与排名的统一汇总。

## Impact

- 影响 `ledGame-platform/server` 与 `apps/member-admin`：服务端增加旧协议监听／路由、适配服务、房间状态投影、SQLite 会话关联及必要迁移；会员管理端只调整旧端房间与记录的诚实呈现。主 API 8090 保持不变，增加旧端固定使用的 16668 HTTP 入口。
- 旧端来源 IP 是旧房间唯一身份；兼容状态在会员管理端房间列表中可见。一个旧游戏端应使用一个可区分的来源 IP；共享 NAT 下无法区分多台旧端。
- 旧版 `cmd=3` 没有会话 ID、结束原因、请求序号或重试机制。兼容层能在常规顺序下关联并防重复结算，但不能从协议本身判定丢失／乱序回调对应哪一局；方案必须明确并安全处理此边界。
- 旧端积分以最终上报值为准，采用与新版计分规则隔离的来源标记；SQLite 现有积分汇总是排行榜和会员信息的共同数据源。
- 兼容端口与主服务共用会员管理端应用生命周期、数据库和现有启动／授权约束，不单独启动第二份后端。
