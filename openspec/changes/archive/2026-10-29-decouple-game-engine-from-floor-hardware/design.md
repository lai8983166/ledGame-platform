## Context

现有 `GameRuntimeFactoryRegistry` 根据游戏 type/mode 选择 factory，玩法通过 `GameHandler` 参与输入和关卡运行。可以沿用这两个入口承载硬件职责。

目前 `GameLaunchService.confirm` 按全局启用的输出名称检查 ELC408，条件是 `RuntimeMode.PRODUCTION`，与触屏、手环或投币启动方式无关。`Stage`、地砖 GIF 服务及引擎待机循环直接调用 `EventPusher`；引擎直接初始化和清理 `PixelLightDisplayUtils`。`TcpLedOutputManager` 在应用级建立输出连接和踩踏监听。符号灯已按游戏解析布局，但物理输出仍为空 sink，不能在此重构中宣称完成真实灯具接入。

ELC 的 `conf.json` 和 `wiring.json` 是设备/场地配置。数据库中的游戏 `wiringData` 属于既有编辑数据，目前没有进入 ELC 游戏运行链路；本次不趁重构改变它的用途。

## Goals / Non-Goals

**Goals:** 当前玩法决定启动检查、输入输出和硬件资源生命周期；既有四种地砖玩法保持原来的行为；通过一个仅测试使用的无地砖玩法验证无 ELC 依赖。

**Non-Goals:** 不新增客户可选玩法、通用硬件插件框架、硬件能力注册中心、设备绑定数据库或硬件配置 UI；不改变 SDK 协议、布线格式、物理符号灯支持程度或游戏规则。

## Decisions

### 1. 复用 factory/handler，以默认空操作支持无硬件玩法

在现有 `GameRuntimeFactory` / `GameHandler` 上补充最少的准备检查、帧输出和运行资源生命周期扩展点。未声明硬件行为的实现默认不检查设备、不发送地砖报文、不初始化外围灯。通过已选中的 runtime 调用扩展点，公共启动入口不再根据字符串 `elc408-sdk` 为每个游戏强加检查。

Simple/Normal/Diffcult 与 Rank 的实际 factory/handler 显式接入一个共享的地砖硬件辅助类，该类可以直接使用 ELC SDK、TCP 输出及外围灯工具。保持现有 type/mode 匹配与冲突校验；不以游戏名称、封面或是否有符号灯配置猜测它是不是地砖玩法。

采用已有入口便于控制变更范围。每种玩法复制 SDK 代码会重复维护；新增通用设备接口和硬件 profile 数据模型超出当前需求，均不采用。

### 2. 保持正式模式检查时机与调试行为

选出 factory 后，由该玩法执行准备检查；地砖玩法仍在正式模式下、会员游玩会话开始和引擎确认准备之前验证已启用的 ELC 输出。失败保留现有错误码，且不开始扣时、不误报游戏已开始。没有启用 ELC 输出时保留现有处理规则。

模拟模式仍允许没有控制器时启动；当 SDK 已启用且设备可用时，地砖调试仍能驱动真实设备。运行模式决定检查策略，触屏/手环/投币决定业务放行，二者不混用。

### 3. 所有地砖帧走同一玩法输出路径

把游戏帧输出从 `Stage` 中的全局硬件调用改为委托当前玩法。地砖 GIF/开始/关卡/结算/结束媒体帧也使用当前局的同一输出入口，避免只改正常运行帧而留下旁路。共享地砖实现继续使用原编码器、序号规则、尺寸和异步 TCP 队列，DebugPanel 的帧流及媒体预览保持兼容。

通用引擎仍可以调度帧、媒体和状态，不需要知道具体 SDK、控制器、端口或符号灯。未来无地砖玩法的帧不会进入地砖发送器。

### 4. 输入归属当前玩法，保持真实与模拟入口统一

保持既有踩踏接口和 DOWN/UP/RESET 语义，物理输入与 DebugPanel 输入进入相同玩法处理路径。地砖坐标边界校验由地砖实现负责；无地砖玩法收到这些旧地砖入口的事件时安全忽略，不改变其分数、状态或会话。烤机注入入口、首个 input-enabled 输出的去重规则继续有效。

SDK 的应用级 socket 可以继续保持连接。将事件交给当前玩法并不要求每换一局都重建 SDK；本次不修改稳定工作的接收线程和连接恢复策略。

应用启动时 SDK 文件损坏或端口绑定失败也不能使整个后端无法启动：保留未加载状态和 `ELC408_RUNTIME_LOAD_FAILED` 健康诊断。正式地砖玩法的准备检查仍重新加载并返回原错误码，工具页仍可修复配置后重新加载。缺少文件和 SDK 关闭沿用原行为。

### 5. 外围灯状态与清理绑定本局

使用地砖/外围灯的玩法在本局启动时冻结原 `pixelLightWiring`，并在结束时清理。复用现有解析器、映射器、可捕获 sink 和默认空物理 sink，不引入未经验证的实际灯光报文。

清理覆盖自然结束、手动停止、启动失败、异常、待机恢复和排队切换。根据实际已获得的资源清理，重复调用安全；延迟执行的旧局输出或清理不能影响下一局。配置缺失、`open=0`、配置非法仍关闭外围灯并保持地砖游戏正常运行。

### 6. 待机与硬件健康属于应用行为，独立于某局玩法

现有系统待机 16×36 彩虹、准备界面的彩虹和旧游戏待机内容由一个具体的地砖待机辅助实现承接；引擎只通知待机/准备状态切换，不直接发送控制器报文。所有进入游戏路径继续停止旧待机循环；无地砖玩法运行中不得被待机帧穿插。

房间连接每 60 秒异步搜索并上报硬件状态的行为保持独立；它用于观察门店设备，设备离线不能因此阻止无地砖玩法运行。SDK 工具页仍可独立使用，搜索不得因移入玩法职责而同步阻塞游戏。

## Risks / Trade-offs

- [漏掉 GIF、待机或直接启动的输出入口] → 先记录所有发送与启动入口，为各路径加行为对比测试，确认不存在跨玩法的全局发送旁路。
- [资源清理抢占下一局或遗漏输入 RESET] → 使用现有会话/run token 边界验证旧局晚到回调、连续切换和重复清理。
- [移动硬件检查改变会员扣时/排队失败行为] → 固定检查先于游玩开始的顺序，回归失败后可重试及队列推进流程。
- [共享地砖代码变成新的复杂框架] → 只提取现有代码，优先复用已有扩展点，不添加仅有一个实现的设备层层封装。
- [模拟测试不能证明现场电气与网络行为] → 软件验收固定现有报文与输入契约，真实地砖链路使用现有简短实操清单；无真实设备时明确记录未完成的实物项。

## Migration Plan

先补充行为基线与无地砖测试夹具，再移动启动检查、输入输出、外围灯和待机职责，最后进行游戏后端、游戏端及核心流程回归。旧游戏由原 factory 显式接入地砖实现，无须更新数据库、SDK 配置或客户操作步骤。

实施完成后重打包游戏端原位置 `win-unpacked` 和 ZIP，检查内嵌后端启动和现有调试入口。回退仅恢复本次运行时改动及游戏端包，不恢复或覆盖业务数据库。
