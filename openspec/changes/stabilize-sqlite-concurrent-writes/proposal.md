## Why

本机双代理并发 smoke 中，16 条注册与游戏流程只有 3 条成功，其余 13 条都在手环充时阶段收到 HTTP 500；这说明会员管理端当前的 SQLite 连接方式不能承受真实门店中多台自助注册端和游戏端同时写入。必须提升生产后端本身的写入稳定性，而不是在测试脚本中降低并发或自动重试来掩盖锁冲突。

## What Changes

- 为会员管理端后端建立统一、可测试的 SQLite 连接策略，使所有业务连接启用 WAL、有限等待锁释放，并使用与 SQLite 单写者模型匹配的连接池配置。
- 保持现有充值、注册、绑定、激活、开局和结算 HTTP 成功契约不变；正常的并发请求由服务端协调，不要求自助注册端或游戏端增加重试。
- 当数据库在规定等待时间内仍不可写时，返回明确的 `DATABASE_BUSY` 服务异常和中文排查提示，不再暴露无含义的通用 HTTP 500。
- 增加真实临时 SQLite 文件上的并发集成测试，覆盖混合业务写入、数据数量与关联核对、锁等待耗尽和备份兼容性。
- 使用现有打包版多点并发验收工具重新执行 smoke，以“非预期 5xx、SQLite 锁错误和数据差异均为零”作为完成条件。

## Capabilities

### New Capabilities

- `sqlite-concurrent-write-stability`: 约束会员管理端 SQLite 的连接初始化、并发写入等待、锁超时错误语义以及真实数据库并发验收标准。

### Modified Capabilities

无。

## Impact

- 影响 `server` 的数据源/Hikari 配置、SQLite 连接初始化和统一异常响应。
- 影响会员、手环、游戏记录、积分、操作日志及备份任务共用的生产 SQLite 连接行为，但不修改现有成功响应结构和业务规则。
- 新增服务端真实 SQLite 并发集成测试，并复用 `add-packaged-multipoint-concurrency-acceptance` 已实现的外部验收工具。
- 不需要修改自助注册端或游戏端，也不引入新数据库、消息队列、客户端自动重试或自建通用写队列。
