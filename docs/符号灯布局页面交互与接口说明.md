# 符号灯布局页面交互与接口说明

## 1. 页面用途

这个页面只负责配置游戏的外围灯具布局：

- 方形符号灯（显示数字、字母、图标等）；
- 圆形灯（普通 RGB 灯，也可作为按压输入）；
- 两种灯分别连接到哪个控制器端口；
- 四面墙各有多少个灯；
- 灯链的起点、方向和地砖对齐坐标。

右侧黑色区域是预览画布，中间的网格是地砖。外围彩色框表示四面墙，白色方块表示符号灯，白色圆点表示圆形灯，箭头表示两条灯链的连接方向。

该页面不是独立保存页面。页面内所有修改先保存在前端内存，必须点击游戏编辑器外层的“保存”按钮才会写入后端。

## 2. 页面初始状态

Default 编辑器的默认值是：

```json
{
  "selectedRow": "0|0",
  "form": {
    "open": 0,
    "controlIdx": 0,
    "pixelPort": 6,
    "circlePort": 7,
    "order": 1,
    "forceAlign": 0,
    "topWallPixelLightNum": 0,
    "rightWallPixelLightNum": 0,
    "bottomWallPixelLightNum": 0,
    "leftWallPixelLightNum": 0
  },
  "rows": []
}
```

注意：界面显示端口号从 1 开始，保存值从 0 开始。例如界面显示符号灯端口 7，实际保存为 `pixelPort: 6`。

## 3. 页面元素和交互行为

### 3.1 “绘制”按钮

按钮只调用组件内部的 `draw()`：

1. 校验当前表单；
2. 清理旧的预览图形；
3. 根据四面墙数量重新绘制墙体；
4. 绘制方形符号灯和圆形灯；
5. 绘制两条灯链的箭头和方向。

不会发送 HTTP 请求，也不会写数据库。

按钮只有在 `状态=打开` 时显示。

### 3.2 状态

选项为：

- `打开`：启用布局字段和预览；
- `关闭`：禁用外围灯运行支持。

源码中的关闭行为有一个副作用：设置为关闭时，会把四面墙数量全部设为 0，并重建空的 `rows`。原来的对齐坐标会因此丢失。

如果新项目实现，建议关闭时只修改 `open`，不要删除数量和坐标配置。

### 3.3 主控序号

选择外围灯连接的主控制器。

界面选项：

```text
1、2
```

实际保存：

```text
界面 1 -> controlIdx = 0
界面 2 -> controlIdx = 1
```

它决定运行时匹配哪一个控制器，页面修改时不请求接口。

### 3.4 符号灯端口号

选择方形符号灯使用的端口，界面提供 1 到 8。

保存时转换为 0 到 7：

```text
界面端口号 - 1 = 后端 pixelPort
```

运行时如果 UDP 数据属于该控制器、该端口，就读取符号灯状态数组，而不是读取普通地砖帧。

### 3.5 圆灯端口号

选择圆形灯使用的端口，界面提供 1 到 8。

保存字段为 `circlePort`，同样是 0 到 7 的下标。

圆形灯端口和符号灯端口不能相同。旧代码没有阻止重复端口；如果重复，运行时符号灯端口判断会优先，圆形灯可能无法正常输出。

### 3.6 接线顺序

选项含义：

- `顺时针`：按上、右、下、左方向组织灯链；
- `逆时针`：反向组织灯链。

当前页面的下拉框被禁用，默认保存为 `order: 1`，用户无法正常修改。代码仍保留逆时针分支，但该分支存在上墙坐标计算使用错误数量的潜在 Bug。

### 3.7 与地板强制对齐

选项为“是/否”，保存字段为 `forceAlign: 1/0`。

当前反编译代码中，这个字段只在编辑器表单中显示和保存，后端运行逻辑没有读取它。它不会自动生成或校验 `rows[].align`。

新项目应选择一种明确行为：

- 删除这个选项；或
- 开启时强制要求每一行都有合法 `x,y` 坐标。

### 3.8 四面墙数量

四个数量控件分别是：

- 上墙符号灯数量：`topWallPixelLightNum`；
- 右墙符号灯数量：`rightWallPixelLightNum`；
- 下墙符号灯数量：`bottomWallPixelLightNum`；
- 左墙符号灯数量：`leftWallPixelLightNum`。

每个控件由“减号、数字、加号”组成，最小值为 0。

修改数量后会触发表格重建：

1. 按四面墙数量生成新的 `rows`；
2. 新行的 `align` 为空；
3. 如果旧行的 `wall|idx` 仍存在，则保留旧的 `align`；
4. 数量减少时，被删除行的坐标丢失；
5. 右侧预览中的灯位数量同步变化。

灯位总数为：

```text
top + right + bottom + left
```

每一个逻辑灯位对应一个符号灯和一个圆形灯。

### 3.9 “请勾选起点”和表格勾选框

表格每行有一个选择框，用于设置灯链起点。

源码限制只有 `idx == 0` 的行可选择，也就是每面墙的第 1 个灯。选中某行后：

1. 设置 `selectedRow = wall + "|" + idx`；
2. 清除其他行选择；
3. 只保留当前起点的选中状态。

它不会立即改变设备，也不会调用 API。它只决定保存后的灯链逻辑起始位置。

### 3.10 墙面列

墙面编号和颜色固定：

| 编号 | 页面显示 | 预览颜色 |
|---:|---|---|
| 0 | 上 | 红色 |
| 1 | 右 | 绿色 |
| 2 | 下 | 蓝色 |
| 3 | 左 | 紫色 |

截图中 `bottom` 显示为英文，是前端翻译缺失，不影响数据。

### 3.11 序号列

序号是墙内序号，界面从 1 开始，保存的 `idx` 从 0 开始。

例如右墙数量为 2，表格显示：

```text
右墙 1 -> { wall: 1, idx: 0 }
右墙 2 -> { wall: 1, idx: 1 }
```

序号不是整条灯链的全局编号。全局编号由后端结合起点、方向和四面墙数量计算。

### 3.12 对齐到输入框

输入格式：

```text
x,y
```

允许为空，或必须匹配：

```text
^\d+,\d+$
```

输入非法时显示红色边框，并且不会向父组件提交新值。

合法值会写入对应行：

```json
{
  "wall": 1,
  "idx": 0,
  "align": "16,14"
}
```

坐标是地砖坐标，界面从 1 开始。该字段主要供需要“外围灯与地砖联动”的玩法使用，例如 `Beach Landing`。普通只控制外围灯的玩法可以留空。

### 3.13 右侧预览

预览只反映前端当前内存状态：

- 中间网格：场地地砖；
- 四周矩形框：四面墙示意；
- 白色方块：符号灯位置；
- 白色圆点：圆形灯位置；
- 橙色/黄色箭头：符号灯链方向；
- 青色箭头：圆形灯链方向。

当填写 `align` 后，预览会按该坐标移动对应灯位；为空时使用自动均匀分布。

预览绘制不代表设备已经输出，也不代表数据库已保存。

## 4. 前端数据结构

组件最终维护的是：

```json
{
  "selectedRow": "3|0",
  "form": {
    "open": 1,
    "controlIdx": 0,
    "pixelPort": 6,
    "circlePort": 7,
    "order": 1,
    "forceAlign": 0,
    "topWallPixelLightNum": 2,
    "rightWallPixelLightNum": 2,
    "bottomWallPixelLightNum": 2,
    "leftWallPixelLightNum": 2
  },
  "rows": [
    { "wall": 0, "idx": 0, "align": "" },
    { "wall": 0, "idx": 1, "align": "" },
    { "wall": 1, "idx": 0, "align": "" },
    { "wall": 1, "idx": 1, "align": "" }
  ]
}
```

实际 `rows` 还会包含下墙和左墙项目。整个对象嵌套在：

```json
{
  "commonConfig": {
    "pixelLightWiring": {}
  }
}
```

## 4.1 符号灯、圆形灯与控制器通信

布局页面本身不向灯具发送实时数据。它只保存控制器、通道和灯位布局；游戏运行后，玩法逻辑才会持续产生灯光状态。

### 4.1.1 输出通信链路

```text
玩法 Level/Handler
  -> PixelLightDisplayUtils.pixelDisplay/circleDisplay
  -> pixelRGBList / circleRGBList
  -> EventPusher
  -> UDPResponseFactory.createResponses
  -> UDPResponsePusher.push
  -> UDP 广播
  -> 控制器
  -> 对应物理灯具
```

符号灯和地砖使用同一套 UDP 发送基础设施。UDP 包中没有“这是符号灯帧”或“这是地砖帧”的独立类型字段，主机在组包时根据布局配置决定每个控制器通道使用哪一类数据。

假设布局为：

```json
{
  "controlIdx": 0,
  "pixelPort": 6,
  "circlePort": 7
}
```

主机组包时的逻辑是：

```text
控制器 0、通道 6 -> pixelRGBList，发送给方形符号灯
控制器 0、通道 7 -> circleRGBList，发送给圆形灯
其他通道         -> 普通地砖矩阵映射结果
```

因此界面中的“端口号”是控制器数据包中的通道下标，不是 UDP 网络端口。真正的 UDP 网络端口只有一个，由应用配置 `udp.send.port` 指定。

### 4.1.2 方形符号灯数据

玩法调用 `pixelDisplay(gameId, color, value, index)` 后，系统生成：

```text
RGB(颜色编号, 符号编号, 0)
```

例如：

```text
RGB(21, 8, 0) -> 蓝色数字 8
RGB(11, 255, 0) -> 绿色整块点亮
```

该 RGB 值被放入 `pixelRGBList[index]`，然后写入配置指定的 `pixelPort` 通道。控制器通常只负责按通道输出数据，是否把数值解释成数字、字母或图标由灯具/控制器固件决定。

### 4.1.3 圆形灯数据

圆形灯调用 `circleDisplay(gameId, rgb, index)`，使用普通 RGB：

```text
RGB.BLUE  -> 蓝色
RGB.GREEN -> 绿色
RGB.YELLOW -> 黄色
RGB.BLACK -> 熄灭
```

状态写入 `circleRGBList[index]`，再发送到 `circlePort` 通道。圆形灯不会使用数字、字母的三字节符号编码。

### 4.1.4 网络地址和控制器识别

当前代码使用当前网卡的广播地址和一个 UDP 发送端口：

```text
network_interface -> dict 表中的网卡名称
udp.send.port     -> 应用配置中的 UDP 目标端口
```

所有监听该广播的控制器都可能收到数据，控制器再根据包内的控制器编号和通道位置决定是否处理。源码没有为符号灯单独配置 IP、网卡、子网或 UDP 端口。

因此：

- 符号灯和地砖可以共用同一个局域网；
- 可以接在同一个控制器的不同通道；
- 也可以接在不同控制器，但仍使用同一广播网络；
- 如果放在另一个子网，当前代码不会自动跨网转发；
- 符号灯和地砖不能占用同一个控制器通道，否则数据会冲突。

### 4.1.5 圆形灯按压输入

当前后端展示出的圆形灯输入入口是 WebSocket：

```text
/ws/default
```

按下事件：

```json
{
  "action": "c-mousedown",
  "controlIdx": 0,
  "port": 7,
  "index": 3
}
```

松开事件：

```json
{
  "action": "c-mouseup",
  "controlIdx": 0,
  "port": 7,
  "index": 3
}
```

后端收到后调用当前玩法的 `_onCircleDown` 或 `_onCircleUp`。布局页面不处理按压规则，具体玩法决定这个灯位是否正确、是否得分或是否触发失败。

源码中没有发现与该页面对应的“符号灯实时控制 REST 接口”。保存接口只保存布局，实际灯光输出发生在游戏运行帧循环中。

## 5. 页面加载接口

### 5.1 编辑已有游戏

```http
GET /game/{id}
```

后端返回游戏对象，其中：

```json
{
  "id": 611,
  "commonConfig": "{\"pixelLightWiring\":{...}}"
}
```

前端加载时执行：

1. 如果 `commonConfig` 存在，执行 `JSON.parse`；
2. 如果没有 `pixelLightWiring`，使用页面默认配置；
3. 解析 `levels`，加载其他编辑器页签；
4. 把 `commonConfig.pixelLightWiring` 传给本布局组件。

### 5.2 新建游戏

新建游戏时没有加载接口，直接使用页面默认配置，直到用户保存。

## 6. 保存接口和数据库写入

### 6.1 保存已有游戏

```http
PUT /game/{id}
Content-Type: application/json
```

编辑器提交的是完整游戏对象，关键字段如下：

```json
{
  "commonConfig": "{\"pixelLightWiring\":{\"selectedRow\":\"3|0\",\"form\":{...},\"rows\":[...]}}",
  "levels": "[...]",
  "wiringData": "{...}",
  "mode": "[1]"
}
```

`commonConfig` 不是对象，而是 JSON 字符串；`levels`、`wiringData`、`mode` 也采用字符串化 JSON。

后端处理步骤：

1. 校验游戏依赖文件；
2. 设置版本、更新时间等公共字段；
3. 调用 `gameService.updateById(game)`；
4. 写入 `game.common_config`；
5. 调用 `PixelLightDisplayUtils.clearCache()`；
6. 返回成功结果。

响应为统一结果对象，成功时类似：

```json
{
  "code": 200,
  "msg": "操作成功"
}
```

### 6.2 新建游戏

```http
POST /game
Content-Type: application/json
```

请求格式与更新类似。后端先保存游戏基本信息，再写入 `levels` 等字段，并保存 `commonConfig`。

### 6.3 页面是否有符号灯专用接口

没有。以下接口都不存在：

```text
POST /pixelLightWiring
PUT  /pixelLightWiring
POST /symbolLight
```

符号灯布局始终作为 `Game.commonConfig` 的一部分，通过游戏整体保存接口提交。

## 7. 数据库字段

数据库表：

```text
game
```

字段：

```text
common_config CLOB
```

示例数据库值：

```json
{
  "pixelLightWiring": {
    "selectedRow": "3|0",
    "form": {
      "open": 1,
      "controlIdx": 0,
      "pixelPort": 6,
      "circlePort": 7,
      "order": 1,
      "forceAlign": 0,
      "topWallPixelLightNum": 2,
      "rightWallPixelLightNum": 2,
      "bottomWallPixelLightNum": 2,
      "leftWallPixelLightNum": 2
    },
    "rows": []
  }
}
```

实际保存时 `common_config` 中存的是上面 JSON 的字符串形式。

## 8. 页面实现清单

实现同等页面至少需要：

1. 维护 `form`、`rows`、`selectedRow` 三类状态；
2. 实现状态、控制器、端口、方向和强制对齐下拉框；
3. 实现四面墙数量调整；
4. 数量变化时重建 `rows`，并按 `wall|idx` 保留旧坐标；
5. 每面墙只允许选择序号 1 作为起点；
6. 校验 `align` 为合法 `x,y` 或空值；
7. 绘制地砖、外围灯位和两条方向箭头；
8. “绘制”只刷新预览，不发请求；
9. 编辑已有游戏时调用 `GET /game/{id}`；
10. 外层保存时把 `commonConfig` 字符串化后调用 `POST /game` 或 `PUT /game/{id}`；
11. 后端把完整游戏对象写入 `game` 表，并清理符号灯缓存。
