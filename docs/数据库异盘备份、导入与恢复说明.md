# 数据库异盘备份、导入与恢复说明

## 功能范围

会员、自助注册、手环、充值、游戏记录、积分、房间设置和操作账号最终都写入会员管理端的 `platform.db`。备份由会员管理端本机后端统一执行，自助注册端和游戏端不需要各自备份数据库。

系统会识别 Windows 的“物理硬盘”，而不是只比较盘符。主数据库在 A 盘、备份目录在同一块物理盘的 B 分区，不算异盘备份。找到另一块可用的本地固定硬盘后，固定目录为：

```text
<目标盘>:\LEDGameBackup\member-admin
├─ latest\platform.db
├─ latest\metadata.json
├─ history\yyyyMMdd-HHmmss-platform.db
├─ history\yyyyMMdd-HHmmss-platform.json
├─ staging\
└─ quarantine\
```

`latest` 随业务变更更新；每天至少保留一份 `history`，默认保留 30 天。目标盘掉线或空间不足不会回滚已经成功的营业操作，管理端会显示降级警告并持续重试。

正式运行和测试运行使用两层隔离：正式备份位于 `LEDGameBackup\member-admin`，元数据标记为 `PRODUCTION`；测试备份位于 `LEDGameBackupTest\member-admin` 或一次性测试目录，元数据标记为 `TEST`。正式程序不会把测试备份列为可导入的固定候选，也不会因为测试库与正式库身份不同而要求处理冲突。自动化测试每次使用独立的临时主库和备份目录，不读取或写入正式备份目录。

旧版本生成的无环境元数据，或误写入正式目录的 `TEST` 备份，会整体移入 `quarantine\environment-mismatch-*`，然后以当前有效主库重建正式备份。原文件会保留，不会静默删除。

## 启动检查

会员管理端启动时先出现独立检查窗口，依次检查本机服务、主数据库、异盘目标和最新备份。该窗口只显示进度和故障原因，不提供数据库导入入口。

- `备份正常`：主数据库与 latest 的实例身份和 revision 一致，可以正常登录营业。
- `备份不可用`：主数据库有效，但没有第二块物理盘、目标掉线、不可写、空间不足或备份失败；仍可营业，界面持续告警。
- `需要维护`：同为正式环境的备份 revision 高于主库，或目标目录属于另一份正式数据库；只开放登录和出厂账号的备份维护区域。
- `数据库已阻断`：主数据库完整性检查失败。此时不自动用备份覆盖主库，应联系厂家执行离线恢复。

系统判断新旧使用数据库内部的实例身份和单调 revision，不使用两个 SQLite 文件的哈希比较新旧。SHA-256 只用于确认某个备份文件自生成后没有被替换或损坏。

## 正常备份与退出

业务提交后，系统会监测主数据库、WAL/SHM 辅助文件和数据库 revision，在配置的防抖时间后创建 SQLite 在线一致性快照。候选文件通过只读 `PRAGMA integrity_check`、核心表检查和 SHA-256 后才替换 latest；失败时保留上一份有效 latest。

正常关闭会员管理端时会显示“正在保存并备份数据”，在有限时间内执行最后一次追赶备份，然后停止本机后端。任务管理器强制结束、进程崩溃或断电无法执行退出钩子；下次启动会根据 revision 自动识别并追赶缺失版本。

不要在会员管理端运行时手工复制、删除或覆盖 `platform.db`、`platform.db-wal`、`platform.db-shm`。

## 登录后导入数据库

数据库导入只允许已登录的出厂账号使用。次级账号看不到入口，直接调用接口也会被后端拒绝。

1. 使用出厂账号登录会员管理端。
2. 进入“设置 → 数据库备份”。
3. 从 fixed latest/history 中选择候选，或点击“选择本地数据库”。
4. 系统只读检查候选的 SQLite 完整性、平台核心表、实例身份、revision、最后业务修改时间和元数据哈希。候选必须恰好包含一个已启用的出厂账号，否则禁止导入。
5. 确认窗口会显示版本、最后修改时间、候选库的出厂账号用户名和会员数量，并明确提示导入后必须使用候选库中的账号登录。
6. 确认后，如果仍有正在运行的游戏或排队，系统拒绝导入。否则进入维护状态，停止后端，保存 `pre-import` 回滚副本，再进行同卷 staging、SHA-256 复核和原子替换。
7. 新数据库重启复验成功后，原登录状态失效，必须使用导入后数据库中的账号重新登录。

取消确认不会修改数据库。允许主动导入旧历史版本，但这会有意覆盖较新的会员、手环、积分和游戏记录，因此必须以确认窗口中的 revision 和最后业务修改时间为准。

如果启动检查发现当前主库有效，但正式备份来自另一数据库或版本更高，出厂账号可在“设置 → 数据库备份”中二选一：

- `导入此版本`：使用所选备份覆盖当前主库。
- `保留当前数据库`：把冲突备份整体移入 `quarantine\kept-current-*`，以当前主库重新建立 latest。该操作不会删除冲突备份。

这两项都必须由出厂账号明确确认，系统不会自行猜测哪份数据正确。

## 导入失败和断电恢复

导入前的主库及其 WAL/SHM 会保存在主数据库同盘的 `data\pre-import\<时间>`。替换过程使用原子维护日志：

- 复制、哈希、替换或新后端复验失败时，Electron 自动恢复 pre-import。
- 导入过程中被强制结束或断电时，下次启动在拉起后端前读取维护日志；只要替换未完成验证，就恢复 pre-import，不使用部分文件。
- 回滚失败时停止继续覆盖，并在启动窗口显示错误，需联系厂家处理。

## 厂家离线恢复

仅在主数据库已经损坏、无法登录认证时执行：

1. 完全退出会员管理端，在任务管理器确认会员管理端和其 Java 后端均已停止。
2. 保留整个主数据库 `data` 目录作为故障副本，不要直接删除。
3. 核对备份旁 `metadata.json` 的 SHA-256，并对候选运行 SQLite `PRAGMA integrity_check`。
4. 先把候选恢复到隔离目录并验证会员、账号、手环和游戏记录，再替换主库。
5. 启动会员管理端，等待启动检查完成，使用恢复库内的出厂账号登录。
6. 验证核心数据后完成一次新业务写入，确认新 latest 的 revision 随之推进。

仓库脚本 `scripts/verify-database-backup-hardware.ps1` 只把 latest 复制到临时隔离路径做验证，不会覆盖真实主数据库。
