## Context

会员管理端 Electron 主进程启动同仓库的 Spring Boot 后端，并将 SQLite 数据库路径设置为 Electron `userData/data/platform.db`。开发桌面版与打包版均采用这一持久化路径；独立自动化测试使用隔离的临时数据库。当前系统只轮换服务日志，没有数据库备份、备份状态或恢复验证。

本能力只面向 Windows 单店部署。备份需要覆盖从自助注册端、会员管理端和游戏端进入同一后端的所有数据库写入，同时不能要求每个调用端参与备份，也不能依靠不同盘符推断不同物理硬盘。

## Goals / Non-Goals

**Goals:**

- 以当前数据库文件所在物理硬盘为源，自动选择另一个物理硬盘上的固定目录。
- 在不停止营业后端的情况下产生事务一致、经过验证、可原子发布的 SQLite 备份。
- 使用数据库实例身份和单调版本明确判断备份属于哪份主库、是否落后或是否出现主库回退。
- 在主界面出现前用独立窗口完成启动检查、必要的追赶备份或明确的降级/阻断判定。
- 只允许已登录的出厂账号在明确确认版本和最后业务修改时间后，将有效备份安全导入并覆盖主库，且替换失败可自动回滚。
- 对未来新增的数据库写入默认生效，避免每增加一个接口就手工补一处备份调用。
- 让管理员能区分“未找到第二块物理硬盘、目标盘掉线、权限不足、空间不足、备份数据库损坏”等状态。
- 通过模拟磁盘拓扑、真实 SQLite 和真实双硬盘 Windows 验收共同证明功能有效。

**Non-Goals:**

- 不实现云备份、NAS 备份、跨机器复制或第三方账号服务。
- 不把实时磁盘镜像当作备份，也不承诺主库与备份在同一瞬间形成跨磁盘原子事务。
- 不允许跳过候选验证、明确确认和维护门禁而静默覆盖主数据库。
- 不备份游戏端、自助注册端的应用文件、配置文件或日志。
- 不处理硬件 RAID、Windows 存储空间内部成员盘的冗余策略；对操作系统只暴露一个逻辑磁盘的阵列按一个源磁盘处理。

## Decisions

### 1. 由平台后端负责备份，Electron 只展示状态

备份协调器放在 Spring Boot 后端，因为后端拥有 SQLite 数据源，能够使用同一 SQLite 驱动创建一致性备份，并能覆盖来自三端的所有业务写入。Electron 主进程继续负责启动后端和转发本机管理请求，会员管理端前端通过只读状态接口展示备份情况。

备选方案是在 Electron 中直接复制 `platform.db`，但这无法保证复制时事务一致；引入 Node 原生 SQLite 模块还会增加 Windows 打包复杂度，因此不采用。

### 2. Windows 磁盘拓扑通过可替换的探测器获取

生产探测器使用 Windows 自带 PowerShell/CIM 获取卷、分区和物理磁盘之间的映射，输出结构化 JSON，至少包含：盘符或挂载点、物理磁盘身份、磁盘编号、总线类型、卷类型、文件系统、可用空间和只读状态。Java 侧不解析本地化的人类文本。

源磁盘由 `platform.db` 规范化绝对路径对应的卷反查得到。物理身份优先使用操作系统提供的稳定 `UniqueId`，其次使用序列号，最后仅在本次运行内使用磁盘编号。无法证明目标与源不同的卷一律排除。

探测器抽象允许单元测试直接注入磁盘拓扑，不要求测试机器真的具备多个磁盘。CIM 不可用、输出不可解析或权限不足分别形成可诊断状态。

### 3. 目标卷采用固定资格条件与确定性排序

候选卷必须满足：本地固定卷、位于不同物理磁盘、已挂载、非只读、可创建探测文件，并具备“候选数据库临时文件 + 已有最新备份 + 安全余量”所需空间。网络盘、光驱、未挂载分区和操作系统标记为可移动的介质不参与自动选择。

候选按稳定物理身份、再按规范化挂载点排序；首次合格者成为目标。系统在状态文件中记录物理身份与卷标识以便重新挂载后优先恢复原目标，但记录不是管理员配置。原目标不可用时允许按同一规则选择其他合格异盘卷。

固定目录为 `<目标卷>:\LEDGameBackup\member-admin`，包含：

- `latest/platform.db` 与 `latest/metadata.json`
- `history/<yyyyMMdd-HHmmss>-platform.db` 与同名元数据
- `staging/` 中可随时丢弃的临时文件

### 4. 使用数据库实例身份和触发器版本作为同步依据

主数据库增加单行内部状态表，保存首次创建后保持稳定的 `database_instance_id`、单调递增的 `database_revision` 和 `last_business_modified_at`。每个需要持久化保护的业务表使用 SQLite `INSERT`、`UPDATE`、`DELETE` 触发器推进 revision 并更新时间；同一事务修改多行时允许推进多次，因为 revision 的用途是建立先后关系而不是统计业务事务数。事务回滚会同时回滚触发器产生的版本和时间变化。

采用数据库触发器而不是要求每个 Service 手工增加版本，是为了覆盖来自三端的所有当前写入以及直接 JDBC 写入。schema 测试维护受保护业务表清单，并要求新增持久化业务表时同时增加版本触发器。状态表自身、SQLite 内部表和纯备份元数据不触发 revision，避免递归。

备份元数据记录其数据库实例身份、revision 和最后业务修改时间。启动比较规则为：身份相同且 revision 相等表示备份捕获到相同业务版本；主库 revision 更大表示备份落后；备份 revision 更大表示主库可能被回退；身份不同表示目标目录中存在另一份门店数据库。后两种情况均不自动覆盖。

文件 SHA-256 只与该文件生成时写入的元数据比较，用来发现备份文件后来被替换或损坏，不用于比较主库文件和备份文件。若版本信息缺失或无法可信读取，系统选择重新验证/备份或进入冲突状态，不根据文件时间猜测“已同步”。

### 5. 文件变化探测负责触发，SQLite 在线备份负责一致性

后端监测主数据库文件及其 SQLite 辅助文件的变化，并以短周期文件属性轮询作为 Windows 文件事件遗漏时的兜底。检测到变化后进入防抖队列；队列允许合并连续写入，但记录首次脏时间，保证持续写入不会无限推迟备份尝试。备份完成后再次比较源文件指纹，若备份期间又发生变化则立即保留下一次任务。

这种方式覆盖当前和未来新增的数据库写入，不要求各业务 Service 手工调用 `markDirty()`。启动时若目标盘可用且没有有效最新备份，也会安排初始备份。

候选数据库通过 Xerial SQLite 在线 Backup API 从活动数据库连接生成到目标盘 staging 文件。它能够得到一致的已提交快照，业务可继续运行；不使用普通 `Files.copy(platform.db, ...)`。若驱动在线备份不可用，任务失败并保持旧备份，不回退到不安全复制。

### 6. 验证通过后再原子发布

候选文件完成后使用独立只读 SQLite 连接运行 `PRAGMA integrity_check`，并读取 schema 与核心表确认它是平台数据库。随后计算 SHA-256、文件大小和生成时间，形成元数据。只有全部通过才将 staging 文件在目标卷内移动并替换 `latest/platform.db`；目标文件系统不支持原子替换时，使用“保留旧文件—替换—失败回滚”的同卷协议。

进程退出或断电后，staging 残留文件在下次启动时清理，不参与恢复。`latest` 在任何时刻都指向最后一份完整验证成功的数据库。

### 7. 最新副本按变更更新，历史副本按自然日保留

每次已提交变更触发的是 `latest` 更新，不为每次写入永久保留完整副本。当会员管理端运行且目标盘可用时，每个门店自然日首次成功备份同时形成一份历史快照；数据库当日无变更时，定时检查仍确保当日存在一份有效历史快照。历史文件默认保留 30 天。

清理顺序为先确认 `latest` 有效、再删除超期历史文件；若历史目录中只剩一个有效副本则暂不删除并记录清理告警。备份元数据使用平台配置时区生成日期，不依赖浏览器时区。

### 8. 备份失败不回滚营业事务，但必须持续可见

跨磁盘备份无法与主数据库提交组成真正的原子事务。业务事务成功提交后，即使目标盘掉线，业务仍返回成功；备份状态改为降级并持续重试。正常目标盘可用时，以提交后 5 秒内开始一次备份尝试作为可测试时限，界面区分“备份中”“备份正常”“备份不可用”和“备份失败”。

状态接口返回稳定错误码和中文可操作说明，包括：不支持的平台、磁盘拓扑探测失败、没有异物理硬盘、目标不可写、空间不足、在线备份失败、完整性验证失败、发布失败。界面在设置页展示完整信息，并在其他管理页面以紧凑告警提示备份处于降级状态。

### 9. 独立启动检查窗口作为业务就绪门禁

Electron 启动后先创建轻量级备份检查窗口，主界面保持未创建或隐藏。检查窗口依次显示“正在启动本机服务、正在检查主数据库、正在检查异盘备份、正在同步备份、检查完成”等阶段，并通过本机只读启动状态接口获得进度；不能只显示一个不可判断是否卡死的加载动画。

后端在启动验证结束前进入 `CHECKING` 门禁，健康检查和启动状态接口可访问，但会修改持久化数据的业务请求返回稳定的“平台正在检查数据备份，请稍后重试”错误。这样即使自助注册端或游戏端先启动，也不会在版本比较期间改变主库。

主库有效且备份同步完成时进入 `READY_PROTECTED`；主库有效但无第二块盘、目标不可写或备份在有界时间内失败时进入 `READY_DEGRADED`，允许营业并在主界面持续告警。主库有效但备份版本高于主库、数据库身份冲突或重装空库发现旧备份时进入 `MAINTENANCE_LOGIN_REQUIRED`，检查窗口完成后只开放登录和出厂账号维护区域，普通营业能力保持门禁。主库损坏到无法认证账号时进入 `BLOCKED`，检查窗口显示原因和厂家离线恢复建议，不开放导入。

启动阶段不直接用主库覆盖异常备份：先分别检查主库与备份完整性及身份版本，再决定追赶。主库有效而备份损坏时可重新生成；主库损坏而备份有效时只能由厂家执行受控离线恢复，因为此时无法可信地从主库读取并认证出厂账号。

启动检查窗口只显示检查阶段、结果和下一步登录/维护提示，不列出候选文件、不显示导入按钮，也不接受导入命令。导入入口只存在于登录后的备份管理区域。

### 10. 正常退出执行收尾备份，异常退出由下次启动追赶

Electron 正常关闭事件先切换到“正在保存并备份数据”状态，请求后端执行 shutdown flush。若主库 revision 高于 latest，且目标可用，则立即生成一次收尾备份；完成或达到配置的有界退出超时后才停止后端。需要相应延长现有托管进程的正常停止等待，但仍保留最终结束进程的上限。

任务管理器强制结束、崩溃和断电无法运行退出钩子。由于 revision 与业务数据在同一 SQLite 事务中持久化，下次启动能够识别主库高于备份并执行追赶。若目标盘在退出时不可用，正常营业数据仍留在主库，退出不会无限等待。

### 11. 导入操作由 Electron 协调停服、原子替换和回滚

候选列表与文件选择仅在当前服务端会话账号类型为 `FACTORY_ADMIN` 时启用。入口优先读取固定备份目录中的 latest 与 history，也允许使用系统文件选择器选择其他本地 `.db` 文件。后端以只读方式打开候选文件，验证 SQLite 完整性、平台核心 schema、数据库身份、候选 revision、`last_business_modified_at`、元数据哈希和应用 schema 兼容性。文件修改时间仅作辅助展示；确认窗口中的“最后修改时间”采用数据库内部的最后业务修改时间。

候选列举、外部文件登记、候选验证、导入准备和确认执行的 API/IPC 每一步都重新检查服务端登录会话及 `FACTORY_ADMIN` 类型，不能把前端按钮隐藏当作权限控制。次级账号和未登录调用统一拒绝，响应不泄露完整候选路径或磁盘物理身份。

候选验证成功后，前端显示：“要将版本为 {revision}，最后修改时间为 {lastBusinessModifiedAt} 的数据库导入吗？导入会覆盖当前数据库。”取消不产生任何磁盘写入。确认前若仍存在进行中的游戏、排队或不可安全中断流程，后端拒绝进入维护状态。

确认后后端切换到 `IMPORTING` 门禁，拒绝三端新写入并完成当前短事务。Electron 获得只在本机有效的导入清单，正常停止后端，将当前 `platform.db` 及其辅助文件保留到同源卷的 `pre-import` 回滚目录，再把候选复制到同源卷 staging，重新核对文件 SHA-256 后原子移动为主库。Electron 不在数据库打开时直接覆盖文件。

替换进度写入原子维护日志，使 Electron 在导入过程中崩溃或断电后能够判断应该继续验证还是恢复 pre-import。新后端启动后再次检查主库完整性、身份与版本；失败则停止新后端、恢复 pre-import 并回到启动检查窗口。

导入本身被记录为新的数据库状态：候选的业务数据、实例身份和最后业务修改时间被保留，同时 revision 推进到高于同一实例已观察到的所有版本，并记录 `imported_from_revision` 与导入时间。这样主动导入旧历史快照不会在下一次启动时被误判成未经授权的主库回退。导入前异盘 latest 和历史副本不删除；若其身份或版本与导入后主库不同，则归档旧 latest，再从导入后主库生成新的 latest。

导入成功后旧登录会话全部失效，管理员使用导入数据库内的账号重新登录。此策略避免导入前账号在数据库被替换后继续拥有不存在的身份。

### 12. 恢复采用停服后的受控流程

恢复说明要求先退出会员管理端并确认后端停止，再校验备份 SHA-256 和 SQLite 完整性，将现有主库保留为故障副本后复制选定备份至主库路径，最后启动应用验证核心数据。仓库提供可重复的验证命令或脚本，但默认不自动覆盖主数据库。

真实硬件验收使用测试专用会员数据，并至少演练一次从异盘副本恢复到隔离主库路径，避免只检查备份文件是否存在。

### 13. 生产与测试备份采用目录和元数据双重隔离

正式运行固定使用 `LEDGameBackup/member-admin` 且元数据环境为 `PRODUCTION`。自动化测试使用每次运行唯一的临时根目录，真实硬件测试使用 `LEDGameBackupTest/member-admin/<run-id>`，二者元数据环境均为 `TEST`。环境不是数据库实例身份的一部分，而是实例身份比较之前的上层边界：环境不匹配或旧元数据缺少环境时，不进入身份/版本冲突判断。

新备份元数据格式升级为 v2 并强制携带环境。生产固定目录中的 v1、无环境或 `TEST` latest 被成对移动到 `quarantine/environment-mismatch-*` 后，以当前有效主库重建正式 latest；不会删除污染文件。固定候选发现只接受当前运行环境的 v2 元数据。出厂账号显式选择的外部数据库仍允许没有配套元数据，但必须通过数据库内容与账号预检。

### 14. 身份冲突提供对称决策而不是强迫导入

身份冲突和备份领先仍禁止系统自动判断哪份数据正确，但出厂维护界面同时提供“导入备份”和“保留当前主库”。后者先可靠隔离冲突 latest，再以当前主库建立新 latest。隔离失败时不覆盖任何文件；新备份失败时解除冲突门禁并进入可营业降级状态，继续显示备份失败原因。

导入候选检查同时读取唯一已启用出厂账号用户名和会员数量。候选缺少唯一有效出厂账号时直接拒绝；确认界面明确说明导入会替换账号数据，并展示导入后需要使用的用户名。系统不读取或展示密码哈希。

### 15. Electron 窗口和托管进程采用显式生命周期

正常启动进入主界面后销毁启动检查窗口，需要导入或退出时再创建。主窗口关闭显式调用 `app.quit()`，不依赖“所有窗口关闭”事件推断，因为隐藏窗口同样会阻止该事件。应用使用 Electron 单实例锁；第二实例只恢复并聚焦已有窗口。

托管 Java 进程先请求正常终止；超时后执行 Windows `taskkill /t /f`，并等待 taskkill 和目标子进程退出或达到最终短上限后才返回。Electron 的退出完成意味着其后端端口已经释放，而不是仅已发起结束命令。

## Risks / Trade-offs

- [Windows 磁盘编号可能在重启后变化] → 优先用 UniqueId/序列号识别，磁盘编号只作运行期回退；每次启动重新解析卷与物理盘关系。
- [PowerShell/CIM 被策略禁用] → 返回独立的探测失败错误，不猜测物理盘关系，也不退化到同盘备份。
- [短时间高频写入导致频繁全量备份] → 防抖并合并请求，同时用首次脏时间设置最长延迟；数据库较小时优先保证恢复点及时性。
- [新增业务表遗漏 revision 触发器会造成错误的同步判断] → 用 schema 契约测试维护受保护表清单，新增表缺少版本触发器时使测试失败；文件变化监测仍作为触发备份的第二道保障。
- [启动检查因故障磁盘响应缓慢而长时间停留] → 每个探测和备份步骤设置超时；只要主库有效，目标盘类错误在有界时间后进入可营业的降级状态。
- [备份版本高于主库时自动选择可能覆盖更新数据] → 不自动判断哪份为真，保留两份数据库并阻断主界面，要求执行受控恢复。
- [导入旧备份会有意恢复旧业务数据] → 确认窗口展示候选 revision 和最后业务修改时间并明确覆盖；导入记录新的活动 revision、保留候选来源和 pre-import 回滚副本。
- [导入时仍有游戏或排队会造成跨端状态与数据库不一致] → 进入维护门禁前检查营业状态，有不可安全中断流程时拒绝导入。
- [导入替换过程中断电可能同时留下新旧文件] → 使用同卷 staging、原子维护日志和 pre-import 回滚副本，下次启动按已完成阶段复验或回滚，绝不使用部分文件。
- [导入后原登录账号可能已不存在] → 所有既有登录会话失效，要求使用导入数据库中的账号重新登录。
- [在线备份短暂占用 SQLite 资源] → 单任务串行、设置忙等待与超时，失败后退避重试；不允许并发备份任务堆积。
- [目标盘突然断开造成 staging 损坏] → 只发布验证成功的候选文件，上一个有效 latest 保持不变。
- [误删除也会进入 latest] → 每日历史快照保留 30 天，latest 不替代历史版本。
- [两块硬盘同时受到整机断电、盗窃或严重电气故障影响] → UI 与文档明确这是本机异盘恢复能力，不等价于异地灾备。

## Migration Plan

1. 数据库迁移先为现有主库创建唯一实例身份、初始 revision 及业务表版本触发器，不改变现有业务表数据。
2. Electron 增加启动检查窗口；升级后的首次启动保持现有 `platform.db` 路径不变，并先验证迁移后的主库。
3. 找到合格异盘卷后创建固定目录并生成、验证首份带身份和 revision 的备份；找不到时以明确降级状态进入主界面，不移动主库。
4. 启动检查窗口只接入检查状态和登录/维护指引；候选预览仅加入出厂账号登录后的备份管理区域，导入实现完成前不显示可点击的覆盖入口。
5. 接入维护门禁、pre-import、原子替换、重启复验和会话失效后，启用带版本及最后修改时间确认的导入入口。
6. 在会员管理端显示备份状态，并将失败详情写入现有服务日志；正常退出接入有界收尾备份。
7. 通过自动化套件后，在真实双物理硬盘 Windows 机器执行中文验收清单、重装导入、旧版本导入、失败回滚、立即关闭/强制终止场景和恢复演练。
8. 若新功能需要回滚，先隐藏导入入口，再停止备份调度、启动门禁与状态 UI；不删除数据库身份/revision 表、触发器、pre-import 或已生成备份，以免破坏可追踪性和恢复能力。
