## Purpose

为打包版会员管理端提供可由两台独立 Windows 压力机共同执行的多点并发验收，并以确定性计划和最终数据核对证明中心 SQLite 在混合注册、绑环、开局和结算压力下没有数据缺失、意外重复、错误关联或积分偏差。

## ADDED Requirements

### Requirement: 中心启动器使用隔离测试数据启动打包版会员管理端
工具 SHALL 在 A 机使用操作者指定的会员管理端打包程序启动测试实例，并在进程启动前为本次 runId 指定独立 userData、SQLite、日志、测试端口、`TEST` 备份环境和备份 root override。

#### Scenario: 启动新的中心测试实例
- **WHEN** 操作者选择有效的会员管理端打包程序并开始一个新 runId
- **THEN** 启动器使用本次运行专属目录和默认测试端口启动同一份打包程序
- **AND** 新实例不得读取或写入正常 userData 及 `PRODUCTION` 备份

#### Scenario: 正常会员管理端或测试端口存在冲突
- **WHEN** 预检发现配置的正常平台服务仍在运行或测试端口已被占用
- **THEN** 启动器须拒绝继续并提示操作者处理冲突
- **AND** 不得结束未知进程或自行猜测其他端口

#### Scenario: 测试实例可被直观识别
- **WHEN** 会员管理端由中心启动器以测试参数启动
- **THEN** 启动检查窗口、主窗口或持续可见区域须显示“并发测试模式”和 runId
- **AND** 正常启动时不得显示该标识

### Requirement: 两台代理无需协调服务即可形成持续并发
系统 SHALL 提供可在 B、C 两台 Windows 机器运行的同一便携代理；两台代理使用相同 runId、不同 agentId 和同一平台地址，并在配置的持续时间内产生重叠业务负载。

#### Scenario: 两台代理执行同一轮测试
- **WHEN** 操作者在 B、C 机使用不同 agentId 启动相同测试配置
- **THEN** 每台代理独立生成互不冲突的数据分区并开始负载
- **AND** 各自输出包含开始时间、结束时间、计划、请求结果和摘要的运行文件

#### Scenario: 代理配置可能造成身份冲突
- **WHEN** agentId、runId、平台地址或安全确认值无效
- **THEN** 代理不得发送任何写请求
- **AND** 须用中文指出需要修正的配置

### Requirement: 代理复现最小持久化业务流程
每台代理 SHALL 同时运行可配置数量的虚拟注册工作单元和游戏工作单元，并仅通过现有生产 HTTP 契约写入中心数据库。

#### Scenario: 注册工作单元完成一次流程
- **WHEN** 注册工作单元执行一个计划项
- **THEN** 它为本次运行专属手环充时、查询或创建本次运行专属会员并完成绑定
- **AND** 请求结果须关联到计划中的手机号、UID 和操作编号

#### Scenario: 游戏工作单元完成游戏循环
- **WHEN** 游戏工作单元完成自身会员和手环准备
- **THEN** 它激活手环，并以唯一外部会话编号依次开始和自然结算单人游戏
- **AND** 每局使用确定性的原始分数，使预期积分可以直接计算

#### Scenario: 两类工作单元混合运行
- **WHEN** 注册和游戏并发数均大于零
- **THEN** 两类流程须不得分阶段串行执行
- **AND** 报告须分别给出两类流程的计划数、尝试数和结果

### Requirement: 完整计划先于负载落盘且核心测试不重试写请求
每台代理 SHALL 在发送业务请求前持久化完整计划，计划中的手机号、UID、设备编号和外部会话编号必须由 runId、agentId、工作单元和序号确定性生成；核心正确性运行 MUST 对每个写操作最多发送一次。

#### Scenario: 代理在执行中退出
- **WHEN** 代理只完成了部分计划便退出
- **THEN** 计划文件和已完成请求结果仍须保留
- **AND** 未尝试的计划项须报告为测试未完成，而不得报告为数据库丢失

#### Scenario: 写请求超时或连接失败
- **WHEN** 代理无法获得确定的 HTTP 响应
- **THEN** 它须记录原业务身份和错误类型并继续遵循配置的停止策略
- **AND** 不得更换身份或自动重发该写请求

### Requirement: 核账器逐项比较计划、请求结果和平台数据
A 机核账器 SHALL 读取 B、C 两台代理结果，并通过会员管理端公开查询接口比较每个已尝试操作对应的会员、手环绑定、游戏记录、结束状态和积分，不得只比较总数或 HTTP 成功率。

#### Scenario: 成功响应对应的数据完整
- **WHEN** 某写操作收到成功响应且最终平台数据与计划字段完全一致
- **THEN** 核账器须将该操作判定为正确持久化

#### Scenario: 成功响应后数据缺失或错误
- **WHEN** 某写操作收到成功响应但最终记录缺失、重复、关联错误、未完成或积分不符
- **THEN** 核账器须列出 agentId、操作编号、业务身份和字段级差异
- **AND** 正确性结论须失败

#### Scenario: 请求失败但平台存在数据
- **WHEN** 请求超时或连接失败，而最终查询发现对应数据已经提交
- **THEN** 报告须将其标为“响应结果不确定但数据已提交”
- **AND** 不得将其误报为数据库丢失

#### Scenario: 两台代理运行时间没有重叠
- **WHEN** 代理结果显示两台机器未形成实际重叠负载
- **THEN** 整体结果须标为测试条件不成立
- **AND** 不得据此宣称已经通过多点并发验收

### Requirement: 正确性结论和性能数据分开报告
默认正确性标准 MUST 要求成功响应后的数据缺失、意外重复、错误关联、未结算记录、积分错误、非预期 5xx、SQLite 锁错误和中心进程退出均为零；吞吐量和 p50/p95/p99 延迟 SHALL 作为独立观测值。

#### Scenario: 数据正确但延迟较高
- **WHEN** 所有数据核对正确但延迟超过建议值
- **THEN** 正确性仍可通过
- **AND** 中文报告须单独显示性能告警

#### Scenario: 出现数据库锁错误
- **WHEN** 请求结果或中心日志出现 `SQLITE_BUSY`、`database is locked` 或等价错误
- **THEN** 报告须归类为数据库并发错误
- **AND** 正确性结论须失败

### Requirement: 测试数据和报告具有明确生命周期及覆盖边界
工具 SHALL 将本次 userData、测试备份、计划、结果和报告放入可识别的 runId 目录；测试数据默认保留且不得由脚本自动删除，关闭测试实例后正常启动会员管理端 SHALL 立即重新使用原正常数据库。

#### Scenario: 测试结束后恢复正常使用
- **WHEN** 操作者正常关闭测试实例并按原方式启动会员管理端
- **THEN** 正常会员、手环、账号和正式备份须与测试前一致
- **AND** 测试产生的数据只存在于本次运行目录

#### Scenario: 生成中文报告
- **WHEN** 核账完成或测试条件不成立
- **THEN** 工具须生成中文 Markdown 和机器可读 JSON，说明配置、两节点结果、核账差异、正确性结论、性能观测和数据目录
- **AND** 报告须明确直接接口负载未覆盖真实 UI、游戏端本地后端、多个房间 IP、控制器、地砖和真实异盘备份拓扑
