## Context

会员管理端打包程序已经支持用 `LEDGAME_USER_DATA` 指定完整数据目录、用 `LEDGAME_PLATFORM_PORT` 指定端口，并能用 `LEDGAME_DATABASE_BACKUP_ENVIRONMENT=TEST` 和 `LEDGAME_DATABASE_BACKUP_ROOT` 创建隔离测试备份。复用现有写入 API；本次定时增强仅给现有只读列表增加可选精确筛选，不新增端点，不直接访问 SQLite。

这个 Change 验证来自两台独立机器的多个逻辑注册端和游戏端并发写入中心服务时，数据是否完整、唯一且关联正确；本次增加执行节奏验收，防止以无限延长时间来补完数据。它不是分布式压测平台，也不负责验证三端 UI、房间在线或硬件。

## Goals / Non-Goals

**Goals:**

- 使用一份打包版会员管理端、两台压力机和现有生产 API 完成可重复的并发正确性测试。
- 测试主库与正常主库隔离，测试结束后不需要恢复或导入数据库。
- 以简单、可读的计划与结果文件核对每一项持久化结果。
- 压力机无需安装开发环境。

**Non-Goals:**

- 自动发现、注册或远程管理压力节点。
- 在代理和 A 机之间维护长连接、租约、心跳或分布式屏障。
- 在脚本崩溃后继续原运行，或对不确定写请求自动重试。
- 自动删除测试数据库。
- 同时验证跨物理硬盘备份、断网、断电、UI、游戏本地后端和真实硬件。
- 构建可扩展到任意节点数量的通用压测框架。

## Decisions

1. **工具只保留三个顺序命令：center、agent、verify。** A 机执行 `center`，生成 runId 并以隔离参数启动打包版会员管理端；B、C 各执行一次 `agent`；两份结果复制回 A 机后执行 `verify`。不运行协调器 HTTP 服务，也不设计节点注册、租约、心跳、任务领取和结果回传协议。三台机器规模固定，少量人工复制文件比维护一套分布式控制面更可靠。

2. **center 复用现有环境变量，不发明数据库模式系统。** 每次运行建立 `<testRoot>/<runId>/member-admin`，设置 `LEDGAME_USER_DATA`、固定测试端口 `18090`、`LEDGAME_DATABASE_BACKUP_ENVIRONMENT=TEST`，并把 `LEDGAME_DATABASE_BACKUP_ROOT` 指向本次运行目录下的 `backup`。这会运行真实备份代码并隔离正式备份，但 root override 不验证物理异盘；真实双硬盘由现有备份专项验收负责。无需修改备份后端来增加 runId 命名空间。

3. **测试模式只增加一个明显标识。** center 传入 test mode 和 runId，会员管理端显示“并发测试模式”。除此以外不新增测试数据库管理 UI、模式切换按钮、自动导入或恢复功能。数据库在应用启动前由环境决定，正常双击启动完全沿用原行为。

4. **center 不成为进程管理器。** 启动前仅检查正常平台地址和测试端口冲突，然后启动打包程序并输出连接信息。测试结束由操作者正常关闭会员管理端，使现有退出备份逻辑执行。脚本不记录或恢复进程树、不批量结束 Electron/Java，也不尝试在崩溃后自动拉起。中心异常退出直接使本次测试失败或未完成。

5. **每台 agent 在请求前一次性写出 `plan.json`。** 完整计划本身就是写前证据，不再为每个操作维护 `INTENT/ACK/RECOVERED` 事件流或折叠状态机。请求完成后按操作编号写入简单的 `results.jsonl`，进程退出时用“计划数与结果数不等”判断测试未完成。

6. **核心正确性运行不重试写请求。** 每个写操作最多发送一次。超时或断连保留原身份并交给最终核账判断：成功响应却缺少数据属于持久化错误；无确定响应但最终存在数据属于响应丢失；无确定响应且没有数据属于请求失败或结果不确定。自动状态查询和重试会增加分支并可能掩盖服务端幂等缺口，因此移除。

7. **保留两个业务流，增加门店节奏。** 每节点 3 个注册工作单元执行“充时 → 查询新／老会员 → 必要时创建 → 绑定”，6 个游戏工作单元准备会员手环后执行“激活 → 单人开局 → 自然结算”；约每三个流程中一个复用前一会员，游戏流同时复用手环，注册流使用新手环。每设备独立随机等待，游戏真实等待 30～180 秒，注册流在两分钟窗口附近集中到店并保留抖动；穿插 5～15 秒间隔的管理查询。不增加多人、故意冲突、排队或跨设备共享手环池。

8. **只开放四档，不实现分阶段状态机。** `quick` 5 分钟、`standard` 30 分钟、`soak` 2 小时、`overnight` 12 小时，设备数与节奏范围固定。随机种子由 runId、agentId、版本常量决定，运行前一次生成全部步骤和绝对相对时间。可离线预览 B/C 合计精确数量；实际慢请求不改变预期。旧 smoke/load 只保留兼容，不作为新定时验收入口。B/C 尽量同时启动，不增加跨机屏障。

9. **数据身份由 runId、agentId、worker 和 sequence 直接派生。** B、C 必须使用不同 agentId。生成器在本机启动前检查自身计划无碰撞；两份计划复制到 A 机后，verify 再检查跨代理碰撞。无需中心分区分配服务。

10. **verify 是纯读取核账器。** 它读取两份 plan/results 文件，重建随机计划校验其完整性，再按手机号、UID 和会员 ID 获取会员、手环、充值、绑定和游戏记录，逐项核对字段、状态及累计积分，并扫描本次中心日志中的 SQLite 锁错误。每会员最多两局、每手环一次充值／绑定，按身份筛选后保留列表 200 条上限也能完整核账。预期按会员／手环去重，不用 HTTP 次数冒充数据库记录数。输出中文 Markdown 和 JSON，不修改平台状态或直接读取 SQLite。

11. **测试运行目录默认永久保留。** 关闭测试实例后，正常启动立即回到正式数据库，因此“恢复”不需要任何动作。测试目录由操作者在确认不再需要报告和复核后按目录整体处理；首版不提供自动删除，避免为便利功能引入递归删除安全逻辑。

12. **使用便携 Node 运行时。** 工具源码使用现有 TypeScript/Vitest 体系，发布目录只携带固定 `node.exe`、编译后的少量脚本、配置模板、许可证和中文说明。相比 PowerShell 并发 runspace、k6 加额外核账器或新增 Go/Java 工程，这与仓库现状更接近且仍能在 B/C 免安装运行。

13. **以原计划检测积压，不顺延时间表。** 用 `performance.now()` 记录原定发送偏移、实际发送偏移和请求耗时。每设备仍串行执行；前一请求慢则后续开始延迟增长，而不是把计划向后改写。结算同时受实际开局成功后的游玩时长约束。每秒采样到点待执行和正在请求数量，并在发送时更新峰值，未来请求不算积压。依赖失败明确跳过，不冒充已执行。配置时长后最多收尾 30 秒；截止不再发新请求，已发送的请求最多等其 5 秒超时。

14. **数据与节奏分别验收，整体同时满足。** 逐请求启动延迟 p95 ≤ 2000ms、无跳过／未执行、实际时长不短于档位且不超过有限收尾要求，才算节奏通过。核账器从原始逐请求证据复算，不能只相信 summary 的通过布尔值。HTTP p50/p95/p99 仍作为独立观测；高请求耗时不能单独归因为数据库排队，发送延迟也可能是压力机过载。报告不承诺精确 MB/GB，SQLite 页面、WAL、日志和备份大小并非固定。

## Ablation Result

以下设计从 Change 中删除：

- coordinator 网络服务及其节点注册、租约、心跳、屏障和状态机；
- agent 自动领取数据分区及自动上传结果；
- 追加式事件溯源账本、事件折叠和协调器崩溃恢复；
- 业务状态感知自动重试；
- 多人、故意冲突、排队和独立突发阶段；
- 新的后端备份 runId 配置；
- 自动关闭未知进程、自动重启复核和自动删除测试目录；
- 把真实异盘备份验收并入并发测试。

它们可以提高自动化程度或扩大覆盖，但都不是回答当前数据丢失问题的必要条件。

## Risks / Trade-offs

- [需要人工把 B/C 结果复制回 A] → 文件只有每台一个结果目录，中文说明固定放置位置；以少量人工步骤换取无协调服务。
- [B/C 启动时间不完全一致] → 使用足够长持续时间，开启 Windows 自动校时并记录两台开始/结束时间；无重叠时结果无效。单节点调度指标不依赖跨机校时。
- [不重试会暴露更多网络失败] → 这正好保留原始事实；报告把请求失败与成功后数据丢失分开，不用补写掩盖问题。
- [测试备份不一定在第二物理盘] → 报告明确只覆盖备份代码同时运行，不声称覆盖异盘；使用已有双硬盘专项清单验证物理拓扑。
- [测试数据占用磁盘] → 每次运行目录清晰独立，文档说明关闭测试实例后可整体移走或删除；工具自身不执行递归删除。
- [12 小时计划与证据增大] → 保留现有简单内存结构，补完整 12 小时计划生成、唯一性、离线核账和资源观察；不把离线结果当作真实通宵验收。真实测试三机须禁用自动睡眠，核账时间不计入负载时长。
- [直接 API 调用绕过游戏本地后端] → 报告明确覆盖边界，真实客户端与硬件继续由其他验收覆盖。

## Migration Plan

1. 建立最小工具目录和配置测试。
2. 实现 center 的隔离启动及测试标识。
3. 实现两类 agent 工作单元、确定性计划和结果文件。
4. 实现 verify 精确核账和中文报告。
5. 打包便携目录，在本机打包版中心＋双 agent 跑 5 分钟验证，再进行实体三机 quick/standard/soak。

回滚只需移除测试工具、命令和测试标识；没有数据库迁移，正常数据路径和正常启动行为不变。

## Open Questions

- 首次三机 standard 后复核默认设备数与 2 秒调度阈值是否适合目标机器；如需调整，明确变更档位版本，不在执行中动态改变验收目标。
