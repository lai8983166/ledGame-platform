## Context

`apps/member-admin` 与 `apps/registration-kiosk` 当前是 Vite Web 应用，仅提供开发、构建和预览脚本。二者在模块加载时从 `VITE_PLATFORM_BASE_URL` 创建 API 客户端，未配置时固定回退到 `http://127.0.0.1:8090`；这对同机开发有效，却无法让另一台自助注册机在交付后选择会员管理电脑。会员管理后端当前在 `application.yml` 固定使用 `8090`，SQLite 默认依赖当前工作目录。

现有游戏端已经证明 Electron 可以携带后端 JAR、精简 JRE、运行时配置和多窗口生命周期。本 Change 借用这种成熟模式，但不把游戏端代码复制成两套难以维护的实现。门店 MVP 继续采用一台会员管理电脑承载中心后端和 SQLite，多台自助注册机只作为网络客户端。

## Goals / Non-Goals

**Goals:**

- 生成两个可在 Windows 上直接运行的独立产品：会员管理端与自助注册端。
- 会员管理端自包含 Spring Boot、JRE、SQLite 路径、日志和端口生命周期。
- 自助注册端从本机运行时配置连接会员管理端，开发和发布都使用同一个双窗口 Electron 架构。
- 所有窗口通过最小 preload/IPC 能力访问配置、进程和业务 API，并具有可自动验证的打包结果。
- 保持默认配置简单：会员管理端端口 `8090`，自助注册端由店员手动测试后启动顾客模式。

**Non-Goals:**

- 不在本 Change 中实现 Windows 服务、无人值守安装、开机自启、自动更新、集中运维或远程控制。
- 不自动修改路由器 DHCP、Windows 网卡 IP 或防火墙；只展示候选局域网地址并提供部署说明。
- 不承诺应用安装后永久免运维，也不覆盖真实多机网络和现场读卡器验收。
- 不改动充值、注册、绑定、玩家查询、游戏准入和结算等核心业务规则。
- 不增加自助注册机本地数据库、会员数据副本或离线写入队列。

## Decisions

### 1. 一个仓库生成两个 Electron 产品，共享桌面基础模块

在 `ledGame-platform` 中增加共享的桌面基础模块，并分别提供 member-admin 与 registration-kiosk 的 main/preload 入口及 electron-builder 配置。两者使用不同 `appId`、`productName`、用户数据目录和输出目录；公共的配置原子写入、受管进程、健康等待、有限日志与资源 URL 解析只实现一次。

选择两个产品而不是单一安装包，是因为它们的权限和资源截然不同：会员管理端拥有 SQLite 与后端进程，自助注册端只能访问远端 API。选择共享模块而不是复制游戏端，是为了复用模式而不建立跨仓库运行依赖。

### 2. 本地打包 UI 始终可打开，业务 API 通过受控 IPC 传输

两个产品的 renderer 在开发时加载 Vite URL，在发布时加载各自 `dist`。preload 按窗口类型暴露窄接口；主进程根据已保存目标执行健康检查和 JSON API 请求，只接受相对 API 路径、允许的方法、有限 body 和超时。共享 API client 增加可插拔 transport，桌面环境使用 IPC transport，纯浏览器预览与既有验收仍使用 HTTP transport。

这比从 `file://` 页面直接 fetch 远端后端更可靠，不需要允许 `Origin: null`、放开全局 CORS 或设置 `webSecurity: false`；也比让所有 UI 由后端托管更能保证后端失败时运维配置页仍可打开。现有零散直接 `fetch` 将迁移到共享 client/transport，防止某些页面绕过运行时地址。

### 3. 会员管理 Electron 拥有后端，但后端仍是单一 Spring Boot 进程

会员管理主进程读取本地配置，检查端口后，用包内 Java 启动包内可执行 JAR，并显式传递：

- `server.port`；
- SQLite 绝对路径；
- 日志目录；
- 必要的 profile/运行标记。

主进程轮询 `/api/health`，健康后才开放业务 UI。修改端口会先校验并征得重启确认，再停止旧子进程、启动新子进程并等待健康；不做动态端口、不做运行中端口迁移。Spring 默认监听所有本机接口，UI 不提供监听 IP 输入；本机管理 UI 始终经 `127.0.0.1` 访问。

SQLite、配置和日志位于 `app.getPath('userData')` 下的稳定子目录，避免安装/解压目录只读和升级覆盖。Electron 只管理自己记录 PID/进程句柄的子进程树，不按名称批量杀死 Java。

### 4. 自助注册端的 operator/kiosk 是正式双窗口状态机

registration-kiosk 主进程始终先创建 operator 窗口。operator 拥有读取/保存 host+port、测试健康连接和启动顾客模式的 IPC；健康测试成功后才创建唯一 kiosk 窗口并隐藏 operator。kiosk preload 只拥有业务 API、只读连接状态和有限的顾客流程能力，不拥有配置 IPC。

kiosk 窗口使用 Electron kiosk/fullscreen，拦截普通关闭。店员通过主进程识别的固定受保护快捷键退出顾客模式，主进程关闭 kiosk 并恢复 operator；网页内容不能直接调用该退出。开发命令仍启动同一个 main/preload，只将 renderer URL 指向 Vite，因此窗口缺陷会在日常开发中出现而不是到打包后才暴露。

### 5. 连接状态由主进程判定，顾客界面只接收脱敏状态

operator 的“测试连接”调用会员管理端 `/api/health`，使用有限超时并区分输入非法、DNS/连接失败、超时、HTTP 非成功和健康载荷错误。kiosk 运行期间由主进程执行有上限的周期健康检查；断线后 renderer 只收到 `ONLINE/OFFLINE` 与稳定错误类别，不收到 host、port、堆栈或日志路径。恢复后回到顾客待机或明确可重试状态，不保留半提交表单。

MVP 不自动启动顾客窗口：应用重启后展示已保存配置，由店员确认连接再启动。以后若要增加开机自启和自动进入 kiosk，应另行增加明确配置和失败回退规格。

### 6. 打包先交付 dir 与 ZIP，构建后执行真实可执行文件冒烟

构建准备脚本先构建两个 Vite renderer、会员管理 Spring Boot JAR和精简 JRE，再分别调用 electron-builder 生成 `dir` 与 `zip`。自助注册端包不复制 JAR、JRE 或 SQLite。构建冒烟从解包目录启动真实 exe，注入测试拥有的数据目录和动态端口，断言本地首页/健康状态后退出并检查无子进程残留。

暂不引入需要管理员权限的 NSIS/MSI，以便先稳定运行目录、配置和数据升级边界；安装程序与防火墙规则可在后续 Change 基于同一便携产物增加。

## Risks / Trade-offs

- [Electron 与精简 JRE 让会员管理包体积较大] → 先复用游戏端已经验证的 jlink 模块集合，并让自助注册包保持无 JRE。
- [端口变更会让已配置终端失联] → 在确认对话框明确提示需要同步修改自助注册端和游戏端，并展示新连接地址。
- [Windows 防火墙可能阻止局域网访问] → 启动诊断区分“本机健康”与“局域网未验证”，文档提供防火墙和跨机冒烟步骤，不伪装成本机测试已覆盖。
- [主进程 API 代理扩大 IPC 表面积] → 仅允许相对 `/api` 路径、白名单方法、JSON 大小限制和按窗口能力隔离，并增加越权测试。
- [开发时 Vite 与发布时本地文件仍有资源加载差异] → 所有业务行为、配置与窗口 IPC 共用；打包目录包冒烟专门覆盖资源路径差异。
- [应用崩溃可能留下后端子进程] → 使用 Windows 进程树/Job 或等价受管关闭机制，并在下次启动通过拥有标记与端口状态给出诊断，不按进程名误杀。

## Migration Plan

1. 先把现有 Web API 调用收敛到可插拔 transport，保持现有浏览器开发与验收测试绿色。
2. 建立共享 Electron 基础模块和自助注册双窗口开发入口，以开发模式测试窗口与配置权限。
3. 建立会员管理桌面入口、后端端口/数据目录注入和受管进程生命周期。
4. 增加两个打包准备脚本、electron-builder 配置和目录包冒烟。
5. 在干净 Windows 用户环境与两台局域网机器完成手工部署演练，再决定是否增加安装程序和防火墙自动配置。

回滚时保留用户数据目录，只停止使用新 exe 并恢复旧的开发启动方式或上一版便携包；不得删除或覆盖 SQLite。端口配置可恢复为 `8090`，其他终端同步改回对应地址。

## Open Questions

- 会员管理端和自助注册端的最终产品名、图标与版本签名证书尚未确定；首轮实现可使用明确的临时产品名和默认图标，但不得共用 appId。
