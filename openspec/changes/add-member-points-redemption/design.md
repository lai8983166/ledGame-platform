# Design

## Context

排名和会员积分已由不可重复结算的游戏记录累计，旧接口使用 pointsTotal / points.total。保留这些来源和字段，不引入第二条游戏积分写入链路。参见 proposal.md。

## Goals / Non-Goals

最小补齐兑换余额和扣减追溯。不改变 GamePlayService、游戏玩法、原排行榜日/月/年口径，不做礼品库存、等级或积分增补。

## Decisions

- schema 10 只新增 member_point_deductions 表，保存唯一请求号、扣减值、前后剩余积分、当时排名积分、原因、时间及操作员快照，并加入现有备份修订追踪。排名积分保持 SUM(已结算 points_awarded)，剩余积分=排名积分-SUM(扣减)，不再维护重复的积分余额列。
- 旧库没有该应用的兑换流水，升级后初始剩余积分自然等于原累计所得，无需复制或重算游戏记录。历史外部系统兑换不凭空推断，后续若有真实资料另行导入。
- 小型 MemberPointsService 只负责扣减、余额查询和记录投影，不建通用钱包/事件层。POST /api/members/{id}/point-deductions 使用 MEMBER_MANAGE，出厂账号、店长、店员均可；正整数积分、必填原因（最多 500 字）、请求号，沿用 SQLite 事务写入策略，检查余额后同事务写唯一记录。服务端拒绝小数/超额及停用会员。
- Member list/CSV 批量投影增加 remainingPoints/rankingPoints，原 pointsTotal 仍指排名积分；Player Info 增加 points.remaining / points.ranking，原 total 仍指排名积分。新前端读取旧响应时回退 total。
- 会员剩余积分旁提供扣减弹窗，详情增加积分扣减记录按钮，查询返回最新 100 条；重试复用请求，未确认结果时锁定参数。新增 DOM 弹窗，保留原焦点恢复。
- 排行榜及会员端副屏继续直接用游戏积分；自助查询只展示两种积分，不获得扣减能力；业务 CSV 增加剩余积分，不另加流水导出框架。

## Risks / Trade-offs

- 并发/重试超扣 → 事务内计算、唯一请求号、现有 SQLite 串行写入，并发测试验证。
- 兑换误降排行或日/月/年分 → 不改游戏记录，查询及榜单前后对比测试。
- 积分尚未结算或反复提交 → 复用原自然结束/中止及结算幂等；新旧端结算回归。
- 查询/导出语义改变旧端 → 保留旧字段累计含义，新增显式字段，旧前端不必改请求。

## Migration Plan

启动时新增表与索引，不写旧积分或历史，重复执行不增加权益。测试均使用临时库和隔离桌面目录。重打会员管理端与自助端，游戏端无需重打；回退用升级前数据库备份，不自动动日常数据。
