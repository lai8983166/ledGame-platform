## Context

会员管理端已经有统一的设置、会员、手环、房间和排行榜 API，但这些能力之间还没有形成完整的门店运营闭环。充值价格仍在服务代码中固定为每分钟 100 分，房间在线投影虽然包含游戏状态，却没有把游戏端的玩家积分映射到会员管理端房间卡片；会员资料只有创建和删除入口；发卡记录只有业务时间，没有操作员快照；副屏也没有一个由会员管理端配置和展示日、月、年排行榜的完整入口。应用标题和窗口图标还需要由桌面端在运行时应用。

本 change 以会员管理端服务为事实来源，复用现有的 operator 鉴权、WebSocket 房间投影和 leaderboard 聚合，不改变游戏计分协议或现有核心流程。需要特别区分“运行时窗口品牌”和安装包/EXE 的编译期图标：本 change 修改前者，安装包图标仍由打包配置决定。

## Goals / Non-Goals

### Goals

- 把应用标题、运行时窗口图标、每分钟充值价格和副屏开关持久化到会员管理端，并让旧数据库得到安全默认值。
- 让房间卡片展示当前游戏和参与会员的实时积分、排名；断线、空闲和数据过期时显示可理解的状态。
- 支持在权限允许的情况下编辑会员资料，并以事务方式校验唯一性、保存加密字段和记录审计事件。
- 让发卡/充值记录保留操作员身份快照、发卡时间与充值时间，兼容历史记录查询和导出。
- 让副屏一次展示日榜、月榜、年榜，数据来自已有真实结算积分，并支持配置开关和断线恢复。

### Non-Goals

- 不修改游戏端的计分规则、关卡逻辑、房间排队协议或控制器协议。
- 不实现远程 OTA、跨门店账号同步或第三方登录找回密码。
- 不在本 change 中改变打包后的 EXE 文件图标；应用图标配置只影响运行时窗口、任务栏和会员管理端页面品牌。
- 不把瞬时房间状态写入 SQLite 作为历史记录；历史积分仍以已结算的游玩记录为准。

## Decisions

### 1. 统一门店设置与默认值

新增一个单例门店设置记录（例如 `store_settings`），保存应用标题、图标资源引用及哈希、每分钟价格（整数分）、副屏开关和更新时间。儿童模式等既有独立开关保持兼容，不强制重构为同一张表。图标文件放在会员管理端受控的用户数据目录，SQLite 只保存相对资源名和校验哈希，避免把大图片作为数据库字段；读取不到或校验失败时回退默认图标。

设置读取接口返回经过规范化的完整值，更新接口按字段补丁处理并要求已有的设置权限。标题去除空白后校验长度，图标限制类型、尺寸和文件大小；价格使用整数分保存，必须为正数。充值服务在同一事务中读取当前价格并写入金额，前端不再自行计算金额。

桌面主进程启动时读取品牌设置，通过 IPC 将标题和图标应用到窗口；设置保存成功后通知主进程立即更新当前窗口。窗口创建早于后端可用时先用默认值，后续收到配置即可替换，不能阻塞应用启动。

### 2. 房间实时积分投影

扩展现有房间状态协议，在 `gameplay.players` 中使用稳定的玩家投影：会员 ID、显示名称、手环 ID（如有）、当前局积分和参与状态。会员管理端服务接收 WebSocket 事件时校验并规范化该数组，在内存中的房间投影上计算并列排名；不把这类易变数据写入数据库。旧游戏端不发送玩家数组时按空数组处理，保持连接和房间卡片的其他字段正常。

房间列表 API 继续返回设置与在线投影的合并结果，前端将投影映射到已有 `Room.players`，房间卡片展示有限数量的玩家、积分和排名，详情抽屉展示完整列表。事件序列号或最后更新时间用于丢弃过期更新；连接断开或超过过期阈值时显示“离线/数据可能过期”，而不是继续伪装成实时。

### 3. 会员编辑

新增 `PUT /api/members/{id}`（或等价的现有 REST 命名）并复用会员管理能力。只允许编辑姓名、手机号、性别、生日和头像等资料字段；会员 ID、删除状态、游玩/交易历史不可通过该接口修改。服务在事务中执行格式校验和手机号唯一性校验，沿用现有 `ProtectedDataService` 的加密/检索哈希策略更新个人数据，并清理被替换的旧头像资源。更新成功写入 operator 审计日志，前端详情页提供编辑、取消、保存和错误回填。

### 4. 发卡/充值审计字段

对 `wristband_charge_records` 做向后兼容的增量迁移，增加 `operator_id`、`operator_username`、`operator_display_name` 快照和明确的 `issued_at`（发卡时间）字段，保留现有 `charged_at` 以兼容旧代码和旧导出。新记录在同一事务内写入当前操作员快照、发卡时间、充值时间、单价和金额；同一操作员稍后改名不影响历史追溯。历史行的新增字段允许为空，界面显示“历史记录/未知”而不伪造身份。

发卡记录和充值记录查询、CSV/备份导出统一返回这些字段。没有操作员上下文时拒绝创建新记录；审计拦截器继续记录请求结果，必要时补充充值配置变更和会员编辑的动作名称。

### 5. 副屏排行榜

复用现有 `/api/leaderboard?period=day|month|year` 聚合逻辑和门店时区，一次请求三种周期并在副屏上并列展示；不复制另一套积分计算。会员管理端的设置开关默认关闭，打开后由桌面主进程创建或显示副屏窗口，关闭后隐藏但不删除窗口状态。副屏按固定间隔轮询三榜，并在窗口重新显示、网络恢复或手动刷新时立即拉取；请求失败保留上次成功数据并显示数据时间和重试提示，不阻塞会员管理主窗口。

副屏只展示已结算的真实积分，日/月/年边界均按服务端门店时区计算。没有数据时显示空榜状态；同分排名规则与主排行榜 API 保持一致。

### 6. 迁移、权限与测试边界

数据库迁移采用可重复执行的 `ALTER TABLE ... ADD COLUMN`/单例初始化，旧数据库启动后自动补默认设置和可空审计字段，不覆盖已有业务数据。设置、会员编辑、发卡记录分别使用已有的设置管理、会员管理、手环管理能力校验；副屏读取排行榜至少需要排行榜查看能力。所有新增 API 在服务层测试鉴权、事务回滚、旧数据兼容和并发更新；前端测试默认值、表单校验、实时房间映射、三榜渲染和离线恢复；桌面测试品牌 IPC 和副屏窗口生命周期。

## Risks / Trade-offs

- 图标资源与数据库分离后，资源文件损坏或被手动删除时只能回退默认图标；通过哈希校验、原子替换和备份资产清单降低风险。
- 房间积分是内存实时投影，服务重启或游戏端断线期间可能暂时为空；这避免高频 SQLite 写入，历史结果仍可从游玩记录查询。
- 旧游戏端可能不发送玩家数组，房间卡片会显示无实时玩家信息，但不会影响现有游戏流程；协议需采用可选字段并在升级后逐步启用。
- 价格配置变更会影响之后的充值金额，不追溯改写历史交易；界面必须明确当前规则和生效时间。
- 新增列和加密快照增加少量写入成本，但只发生在会员编辑和充值等低频操作，不影响游戏帧链路。
- 副屏轮询失败时保留旧数据可能造成短暂误解，因此必须同时显示最后更新时间或“数据可能过期”标记。

## Migration Plan

1. 先发布包含幂等迁移和默认值的会员管理端后端；旧客户端可继续使用，充值仍得到默认的 100 分/分钟规则。
2. 发布 API 客户端和会员管理端 UI，启用品牌、价格、会员编辑、审计列和房间实时投影；桌面端保持默认品牌作为降级路径。
3. 发布支持玩家实时投影和副屏窗口的桌面/游戏端；未升级的游戏端继续按兼容协议连接。
4. 升级后运行数据库迁移、核心 API/权限/并发测试，再手动验证副屏三榜和房间卡片；出现问题时可先关闭副屏开关，保留新增数据库列以便安全回滚代码。

## Open Questions

- 暂无阻塞性问题。图标允许的格式、尺寸和文件大小应在实现任务中采用现有媒体库校验上限，并在 UI 中给出明确提示。
