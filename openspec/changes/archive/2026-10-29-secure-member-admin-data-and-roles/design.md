## Context

会员管理端后端当前使用 Xerial SQLite JDBC 和大量 `JdbcTemplate` 直接 SQL，主库与异盘备份均为普通 `platform.db`。备份通过 SQLite online backup 复制一致快照，并以 `database_state` 修订号和元数据决定启动同步/导入。桌面端与开发桌面版按既有约定共享 Windows 用户数据目录。

账号表的 `account_type` 只有 `FACTORY_ADMIN` 与 `OPERATOR`，前端 `operatorPolicy.ts` 仅区分出厂专属能力；后端只有少量备份/导出接口检查 `X-Operator-Id`，账号管理接口缺少完整授权。自助注册端和游戏端还会调用共享业务接口，因此不能给全部 `/api` 路由粗暴增加操作员登录要求。

现有业务导出由后端直接查询明文字段生成 CSV，再由 Electron 保存到用户选择的位置。会员页和“记录与数据”页目前都有会员导出入口。

## Goals / Non-Goals

**Goals:**

- 复制主库、在线备份或文件日志时不能直接读取会员身份、手环外部标识和敏感操作详情。
- 保持现有手机号/手环精确查询、唯一性、统计聚合、并发写入、备份修订和三端核心流程。
- 使用 Windows 自动保护密钥，不给门店增加日常密码输入或手工密钥文件步骤。
- 建立可测试的三级角色矩阵，前端隐藏与后端授权一致，账号删除不破坏历史审计。
- 让可读 CSV 仍然方便使用，同时明确它是主动生成的明文业务文件而非系统备份。

**Non-Goals:**

- 不引入云端账号、短信找回、第三方密钥管理服务或在线授权平台。
- 不把操作员登录密码、激活码或厂家签发密钥复用为数据密钥。
- 不在本次支持 Windows 重装、Windows 用户变更或跨机器后的自动密钥恢复；这需要独立的恢复密钥/厂家工具方案。
- 不要求自助注册端或游戏端持有数据密钥，也不改变它们的业务响应结构。
- 不对所有状态、时间、数值和内部 ID 机械加密，避免破坏索引、聚合和外键。

## Decisions

### 1. 使用字段级 AES-256-GCM，而不是本次替换为 SQLCipher

受保护值使用版本化信封，例如 `enc:v1:<keyId>:<nonce>:<ciphertext+tag>`，每次加密生成新的 96 位随机 nonce，附加数据包含表名、列名和记录稳定身份，防止密文跨列替换。Java 加密服务只接受已知版本并对认证失败作显式错误。

选择字段级加密是因为现有 Xerial JDBC、SQLite online backup、数据库检查器和大量 SQL 可以继续工作；SQLCipher 会替换驱动与文件格式，并扩大备份/导入/并发回归范围。代价是表结构、记录数量和内部 ID 关系仍可见，但外部身份值不可读。若以后要求隐藏全部数据库结构，再单独评估 SQLCipher。

字段范围：

| 表 | 加密字段 | 保持可查询字段 |
| --- | --- | --- |
| members | phone、name、avatar_id、birthday、gender | id、status、deleted_at、时间、created_by；新增 phone_lookup_hash |
| wristbands | card_uid | id、status、duration_minutes、时间；新增 card_uid_lookup_hash |
| wristband_charge_records | wristband_uid | wristband_id、分钟、单价、金额、时间 |
| wristband_bindings | 无额外文本密文；身份通过已加密的关联表保护 | 内部外键、状态、分钟和时间 |
| game_play_records | wristband_uid、result_json | 内部 member/binding ID、设备/房间/场次/游戏标识、状态、分数、积分和时间 |
| operator_action_logs | operator_username、operator_display_name、target_id、summary_json | operator_id、action、target_type、created_at |
| operator_accounts | 不加密 password_hash；显示名/用户名保持登录和审计定位 | 全部，密码继续 BCrypt |
| room_settings、store_feature_settings、database_state | 不加密 | 全部 |

### 2. 精确查询使用 HMAC-SHA-256 摘要

手机号先按现有规则去空白并规范化，手环 UID 按读卡器十进制字符串规范化，再用从主数据密钥通过 HKDF 派生的独立 lookup key 计算 HMAC-SHA-256。`members.phone_lookup_hash` 取代活动手机号唯一索引，`wristbands.card_uid_lookup_hash` 取代 UID 唯一索引。随机 AES-GCM 密文不得用于等值索引。摘要不使用无密钥 SHA，降低手机号小空间枚举风险。

加解密和摘要收敛在后端数据保护服务；各业务 Service 在参数进入 SQL 前计算摘要、读取行后解密。不得让控制器、前端、自助注册端或游戏端处理密文。

### 3. Java 后端直接使用 Windows DPAPI 管理安装密钥

后端首次发现未初始化的数据保护状态时生成 32 字节随机主密钥，通过 Windows DPAPI CurrentUser 封装，原子写入会员管理端用户数据目录的 `security/data-key.dpapi`。密钥文件包含格式版本、keyId 和 DPAPI 密文，不包含明文。Java 通过最小 Windows 原生桥接调用 DPAPI；生产模式在非 Windows 或 DPAPI 不可用时失败，自动化测试注入临时测试密钥提供器。

使用 CurrentUser 与当前开发桌面版/打包版共享数据库的约定一致。应用升级不删除用户数据目录。密钥仅在后端进程内存存在，不通过配置文件、命令行参数、HTTP 或 Electron renderer 暴露。

### 4. 增加明确的数据保护状态并在启动门禁内迁移

新增 `data_protection_state` 单行表，记录格式版本、keyId、迁移状态和完成时间，不记录密钥。迁移顺序：

1. 在业务主界面开放前取得单实例迁移锁并暂停备份调度。
2. 原子创建或加载 DPAPI 密钥信封，校验 keyId。
3. 在 SQLite 事务中增加查询摘要列/索引、重建需要修改 CHECK 或唯一约束的表，并将已识别明文逐行加密。
4. 校验条数、外键、唯一摘要、关键汇总和抽样解密，提交事务并标记完成。
5. 立即生成一份新的加密态在线备份；目标盘离线时主库仍可营业，但持续显示备份待同步状态。

事务中断时 SQLite 回滚；密钥已生成但事务未提交是安全可重试状态。已标记加密而密钥缺失、keyId 不符或认证失败时不回退成明文、不创建新库，复用启动维护页面给出错误码。

### 5. 备份复制密文数据库并携带 DPAPI 信封

在线备份无需逐字段再次加密，因为主库字段已是密文。`latest` 与新 `history` 元数据增加 `encryptionVersion`、`keyId`，并复制同一个 DPAPI 密钥信封；导入准备阶段先校验元数据和信封，再在临时连接中验证关键密文可解密，最后才允许覆盖主库。

历史明文备份在目标盘可达时识别：有效且与当前实例匹配的备份先迁移为加密态快照，无法确认的移入现有 quarantine 并标注 `PLAINTEXT_LEGACY_BACKUP`，不再显示为可直接导入候选。目标盘离线不阻断主库，但界面必须说明旧目标盘可能尚有待处理明文备份。

DPAPI CurrentUser 只能保证同 Windows 用户环境恢复。跨机器/重装 Windows 的恢复必须另做带独立恢复密码或厂家恢复公钥的 Change，不能通过把明文主密钥塞进备份解决。

### 6. 可读导出在后端解密并直接保存

保留三个 CSV 数据集契约。查询改为获取密文列并在 Java 逐行解密，避免 SQL 直接把密文输出；结果使用流式响应或有界分页，Electron 在用户选定路径执行原子写入，不在默认临时目录落明文。当前数据规模下 AES-GCM/HMAC 开销相对 SQLite I/O 很小，聚合用的积分、金额、状态和时间保持明文，因此运营总览和排行不会全表解密。

CSV 是用户主动产生的明文，界面明确提示保管风险。出厂管理员与店长可导出；店员不可进入记录页，后端导出接口仍重新校验账号。导出审计只记录数据集、操作人、时间、成功/失败，不记录正文和保存路径中的用户隐私。

### 7. 三级角色与能力矩阵由后端做最终判断

数据库角色使用 `FACTORY_ADMIN`、`STORE_MANAGER`、`CLERK`；迁移重建 `operator_accounts` 的 CHECK 约束并把 `OPERATOR` 改为 `CLERK`。增加 `deleted_at` 实现逻辑删除，正常登录和列表过滤已删除账号，历史 `operator_action_logs.operator_id` 不变。

权限矩阵：

| 能力 | 出厂管理员 | 店长 | 店员 |
| --- | --- | --- | --- |
| 手环全部日常操作 | 是 | 是 | 是 |
| 会员查询/新增/修改 | 是 | 是 | 是 |
| 删除会员 | 是 | 否 | 否 |
| 运营总览、房间、记录、排行 | 是 | 是 | 否 |
| 三类 CSV 导出 | 是 | 是 | 否 |
| 儿童模式等功能开关 | 是 | 是 | 是 |
| 创建/管理/删除店员 | 是 | 是 | 否 |
| 创建/管理/删除店长 | 是 | 否 | 否 |
| 数据库导入、端口和出厂维护 | 是 | 否 | 否 |
| 修改本人密码 | 是 | 是 | 是 |

这里的“不能执行删除操作”定义为不能删除业务数据或越级删除账号。清除余额、回收和解绑是有审计记录的手环状态操作，属于用户明确授予店员的手环管理范围；如果产品上希望把其中某项视为删除，应在实施前调整矩阵。

后端 `OperatorAuthorizationService` 增加具名能力检查，所有管理员专用接口显式声明能力并每次从数据库读取账号状态。仍沿用当前 `X-Operator-Id` 本地身份模型，不引入令牌；它防止正常界面和误调用越权，但不宣称抵御拥有数据库和本机管理员权限的攻击者。自助注册端/游戏端所需机器接口建立明确允许列表，不要求操作员头。

### 8. 设置页按角色分区，导出入口去重

前端能力策略映射与后端矩阵建立镜像契约测试：店员导航只显示手环、会员、设置；设置只显示儿童模式等功能开关和本人密码。店长可见业务页及店员账号区；出厂管理员可见全部维护区。后端 403 时统一提示权限不足并刷新/清除失效身份。

删除 `MembersView` 的会员导出按钮与说明，保留 `RecordsView` 中会员、交易和游玩三个导出入口，并按角色隐藏。账号管理增加角色选择、目标范围和逻辑删除确认；店长表格不返回不可管理的店长/出厂账号。

## Risks / Trade-offs

- [字段加密遗漏某条 SQL 路径，向界面返回密文] → 先建立敏感列清单和数据库明文扫描测试，再逐个更新服务与导出查询；禁止控制器直接输出原始行。
- [随机密文破坏唯一性或幂等] → 所有等值查询在迁移前建立 HMAC 索引测试，保留内部 ID/外键和非敏感幂等键。
- [DPAPI 密钥丢失导致数据不可恢复] → 密钥信封随同异盘备份保存并在每次备份验证；缺失时阻断写入。明确当前只支持同 Windows 用户环境恢复。
- [迁移期间断电或磁盘满] → 单事务、启动门禁、预检可用空间和迁移后汇总校验；失败不删除原数据结构、不启动备份覆盖。
- [旧备份仍含明文] → 目标盘上线时迁移或隔离全部已识别旧候选并持续提示未处理状态；不把未知文件自动删除。
- [角色限制只在前端] → 管理员专用后端接口逐项增加能力检查与 403 测试；共享机器接口单独列出，避免一刀切破坏三端流程。
- [CSV 导出重新产生明文] → 仅授权角色主动导出、明确提示、直接写用户选择位置、不留临时副本并记录最小审计。

## Migration Plan

1. 先增加加密/摘要/DPAPI 的纯单元测试、临时 SQLite 迁移夹具和三级权限矩阵测试，不接触开发/生产数据库。
2. 增加 schema 版本与数据保护状态，使用包含全部十张现有表及历史数据的副本验证明文到密文迁移、旧账号到店员迁移和断点恢复。
3. 更新全部敏感数据读写、查询、审计与导出路径；运行核心流程、并发写入、备份/导入和三端大型验收测试。
4. 更新前端导航、设置分区、账号管理及导出入口；覆盖三个角色的界面和后端越权测试。
5. 打包会员管理端，在隔离 Windows 用户数据目录实测首次迁移、重启、异盘备份、同机恢复和密钥缺失维护提示。
6. 正式升级前保留一份离线受控的原始数据库副本作为人工回退材料；一旦新版本产生加密后业务写入，不允许直接降级旧版本继续写同一数据库。
