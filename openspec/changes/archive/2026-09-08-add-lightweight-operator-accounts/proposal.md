## Why

会员管理端目前只有演示账号外观，无法要求店员登录、区分出厂管理员与普通操作员，也无法在业务记录中标明实际操作人员。项目定位为低成本、可信局域网内运行的门店产品，因此需要的是防误操作和人员留痕，而不是面向恶意攻击者的互联网级鉴权系统。

## What Changes

- 在 Platform SQLite 中增加轻量操作账号，账号类型固定为 `FACTORY_ADMIN` 和 `OPERATOR`，密码使用标准不可逆摘要保存。
- 数据库首次初始化时建立一个可通过出厂配置确定用户名和初始密码的最高权限账号；该账号可以创建、修改、启停次级操作员账号。
- 会员管理端启动后先显示登录页面；后端只在登录时验证账号密码并返回账号资料，前端在内存全局状态中保存当前操作账号，退出或重启应用后清空。
- 会员管理端根据当前账号类型显示或隐藏账号管理、会员删除、手环余额清除、房间改名和系统设置等高权限入口；普通操作员保留日常会员、手环、房间查看和记录查询流程。
- 会员管理端的关键写操作携带当前操作账号，后端确认账号存在后记录操作人和操作摘要，不接受前端自由填写的 `createdBy` 作为管理端操作人依据。
- 不提供忘记密码、恢复码、短信、邮箱或第三方登录；出厂账号遗失后按产品规则联系厂家执行重新安装或恢复出厂。
- 明确不引入 JWT、Cookie 会话、Redis、后端逐接口权限拦截、自定义权限组合、自动锁屏或多设备并发会话管理。该机制的目标是业务流程控制和留痕，不承诺抵抗直接调用后端或篡改前端状态。

## Capabilities

### New Capabilities

- `lightweight-operator-accounts`: 覆盖出厂管理员与次级操作员的持久化、一次登录校验、前端内存账号状态、轻量 UI 权限、退出登录和关键管理操作留痕。

### Modified Capabilities

无。

## Impact

- Platform 后端：SQLite schema/migration、账号登录与账号管理 API、密码摘要、管理操作人校验与操作日志。
- 会员管理端：登录页、全局当前账号状态、账号管理界面、侧边栏账号展示与退出、按账号类型控制管理入口。
- 共享 API 客户端与 Electron 桌面传输：增加登录、账号管理和操作账号上下文支持，但不保存或传递安全会话令牌。
- 测试与验收：增加账号初始化、登录、账号管理、UI 权限、操作留痕和应用重启后重新登录测试；现有自助注册端、游戏端及其公开业务接口保持不变。
