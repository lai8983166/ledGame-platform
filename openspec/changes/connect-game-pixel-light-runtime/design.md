## Context

当前游戏后端的地砖输出链路由 `GameEngine`、`EventPusher`、LED 编码器和 `TcpLedOutputManager` 组成；外围灯工具仍为空实现，旧文档描述的 UDP 链路与当前实现不一致。布局数据已经存在于游戏的 `commonConfig.pixelLightWiring`，因此运行时需要在不改动现有地砖报文契约的前提下增加一层外围灯运行时映射。

## Goals / Non-Goals

**Goals:**

- 在每局游戏开始时解析并冻结外围灯配置。
- 用统一、可测试的逻辑把符号灯和圆灯状态映射到控制器及通道。
- 与当前 TCP/编码器链路共存，保持地砖报文行为不变。
- 对无效配置和单个目标发送失败提供明确诊断并降级运行。
- 在所有结束路径清理外围灯状态。

**Non-Goals:**

- 不重新设计 ELC-408 控制器发现、网卡选择或全局 wiring 配置。
- 不在本 Change 中实现圆灯作为按键输入的语义；本 Change 只处理 RGB 输出。
- 不把外围灯配置错误升级为整局游戏启动失败。
- 不复刻旧源码中未经验证的 UDP 报文格式。

## Decisions

### 使用不可变的本局运行配置

游戏开始时从 `commonConfig.pixelLightWiring` 解析出 `PeripheralLightRuntimeProfile`，包括有效目标、逻辑灯序列、通道和对齐映射。运行中只读这份 profile，结束时丢弃。

这样可以避免管理员在编辑器中修改布局或下一局加载新配置时影响当前游戏。备选方案是在每次输出时重新读取数据库或全局静态配置，会造成竞态和跨局污染，因此不采用。

### 先完成逻辑映射，再接入当前输出抽象

将以下部分拆开测试：

1. 根据 `rows`、墙面数量、起点和 `order` 生成稳定的逻辑灯序列；
2. 把逻辑灯状态写入某一控制器/通道的 RGB payload；
3. 将外围灯 payload 交给现有输出管理器。

`order = 1` 按说明解释为顺时针，`order = 0` 为逆时针；映射必须有固定的 golden 测试。旧实现中疑似存在逆时针分支偏移问题，不直接复用其计算结果。

### 保留地砖输出作为独立主路径

外围灯是附加输出。每次生成输出快照时，地砖矩阵仍走原有编码和发送路径；外围灯只追加或合并到当前编码器明确支持的通道结构中。若某外围目标无效或发送失败，只跳过该目标并记录诊断，不改变地砖矩阵。

如果当前协议不能在一个帧中表达多个通道，则在编码器层增加明确的多通道帧模型，而不是在 `GameEngine` 中拼接原始字节或另起一套 UDP 客户端。

### 配置错误采用降级策略

运行时对端口范围、控制器索引、重复通道、墙面行和 RGB 长度做校验。布局无效时 profile 标记为 disabled，并记录具体原因；地砖游戏继续运行。只有现有地砖输出本身失败时，才沿用原有的地砖错误处理。

### 清理绑定到统一生命周期出口

自然结束、手动停止、准备取消、启动失败、异常终止和下一局切换都必须调用同一个外围灯清理入口。清理使用当前有效 profile 发送全黑/空状态，并保证重复调用幂等。

## Risks / Trade-offs

- [当前控制器协议可能无法直接承载多通道 RGB] → 先用编码器和假输出目标建立 golden 测试，再根据实际控制器报文扩展帧模型；不在业务层硬编码字节。
- [外围灯发送失败拖慢地砖发送] → 目标按控制器隔离，设置明确超时/失败记录，禁止外围灯重试阻塞地砖主循环。
- [历史布局字段含义不完整] → 解析器对缺失字段保持关闭/降级，只有完整合法 profile 才启用输出；不改变旧游戏启动行为。
- [清理路径遗漏导致灯光残留] → 为每个结束入口补生命周期测试，并让清理入口可重复调用。
- [实际硬件与文档通道语义不一致] → 先以当前 wiring、控制器和编码器实现为准，使用假输出目标和 golden 报文固定软件契约；真实灯具接入留作后续独立验收。

## Migration Plan

1. 先部署布局编辑器 Change，旧游戏默认 `open = 0`，因此运行时行为不变。
2. 部署运行时 Change 后，只有明确启用且校验通过的布局才产生外围灯输出。
3. 若后续硬件验收发现协议映射错误，可通过关闭布局降级回地砖-only 模式；修复编码器后重新启用。
