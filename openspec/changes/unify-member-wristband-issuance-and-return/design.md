# Design

## Context

CoreFlowController 的 charge/bind 把分钟数存在 wristbands/bindings，GameAccessService 用绑定 started_at 算连续到期。会员查询没有自己的余额；柜台有独立会员/手环页和 clear/unbind/reclaim 多入口。见 proposal.md。

## Goals / Non-Goals

目标是在已有 SQLite 事务、计时、权限、审计和 API 投影内收紧，不建钱包框架或消息命令层。不实施按次数、积分兑换、加密撤销或 RUNNING-only 计时。

## Decisions

### 2026-10-20 修订（优先于以下旧阶段决策）

- members.time_balance_seconds 只保存未分配余额。binding 保存 allocation_seconds、started_at、returned_seconds；账户充值不延长在用卡。发卡立即 ACTIVE，游戏 activate 仅校验，不重置计时。
- 会员独立充值使用一张 member_recharge_records 记录表，关联会员而非手环，保存幂等请求号、可选收款和操作员快照；发卡分配和退回记在原绑定与原审计中，不另建钱包框架。
- 还卡按服务器时间计算秒级剩余，事务内仅退回一次，保留原运行中拒绝还卡与 bindingId 防迟到请求规则。到期不改未分配余额。
- 升级时将旧共享计时账户的实际剩余移至当前绑定，未发卡账户保留；READY 旧卡从升级时开始计时。仅在绑定尚无 allocation_seconds 时迁移，重复运行不加回。
- 会员列表余额旁充值，行内发卡。新增会员支持初始充值。充值与发卡不合并，不嵌套充值；发卡不足提示先充值。列表只显示账户余额，本次剩余放详情/还卡。保留首页发还卡。
- 自助预置卡绑定一次性兑现为本次用卡额度，不再次从会员账户扣除同一份额度。旧 charge/bind、游戏准入字段保持兼容。

### 历史阶段决策（已由上述修订替代，不再按此实施）

- members 增加秒级余额与消费开始时间。READY 发卡只绑定；首次游戏 activate 把会员消费开始时间设置为服务端时间，重复激活不重置。还卡持久化当前剩余秒数并清消费开始时间，binding RETURNED、wristband IN_STOCK。新发卡不用旧卡余额，可换任意空闲实体手环。
- 发卡一个事务完成加时、绑定和充值记录；请求号保存在绑定行，以防网络重试重复加时。还卡确认携带刷卡查询到的 bindingId，防止旧请求把已重新发出的卡归还；重复还卡不重复扣时。运行中的游玩记录拒绝还卡。
- 新柜台入口为运营管理首页顶部两个业务按钮；会员列表保留信息查看/编辑/历史查询。发卡弹窗识别/登记会员，接着读卡器数字+Enter，确认分钟数；还卡刷卡后确认。取消不收费、不解绑，保存会员独立于之后是否成功发卡。不给弹窗添加小标题/说明。
- 首页复用原 RoomsView 和既有轮询、剩余时间时钟、改名接口；卡片只显示名称、IP、状态、剩余游戏时间，点击卡片打开排队/硬件详情。旧房间数据与改名权限不扩展：店员可打开首页办理发还卡，但原本无权查看的房间数据不加载。运营总览只请求统计数据，不再额外请求房间列表。
- 旧 charge 的未绑定分钟数作为待入账充值保留，bind 一次转入会员；充值记录明确关联受益会员，避免循环使用同一卡造成历史串人。游戏接口字段不变，Player Info 增加账户余额投影。
- schema 迁移在事务内一次转移旧 READY/ACTIVE 剩余时长，ACTIVE 以迁移时点计算剩余后继续计时；历史 EXPIRED/RETURNED 不重复加回。只在旧库缺少账户列时迁移，多绑定遗留余额合并后禁止新增重复绑定，不删除身份、积分或历史。

## Risks / Trade-offs

- 导入/重启重复加余额 → 用账户列存在性和事务确保迁移仅一次，测试失败回滚/重跑。
- 旧请求影响换卡后的持有人 → 确认 bindingId 并做发卡请求号幂等。
- 还卡与结算错乱 → 运行中拒绝，还卡不改游戏积分/结果，旧绑定权限随归还失效。
- UI 弹窗后无法输入 → 复用 DOM 弹窗焦点恢复，刷卡只在扫描步骤捕获，姓名/手机号/分钟输入不被拦截。

## Migration Plan

先在临时 SQLite 测试旧数据迁移、发卡/激活/还卡/换卡及并发重试，再回归三端核心 API 与真实 UI。正式数据库只由应用后续正常启动迁移，不直接操作开发机用户库。余额迁移后不可用旧版本继续写库，回退须使用更新前的数据库备份。
